# Smart-table cell edit routed through the canonical record write verb

`table-write.ts` is a 26-line adapter: it builds a `table:` resource ref from a vault path and wraps `writeRecord` with a `set_cell` operation carrying `expected_revision`, `row`, `field`, `value`. It replaces whole-file table rewrites with one bounded, revision-conditioned operation, and carries its governing citation (ADR-002 §15.2 v87; ADR-005 §12 v42 U6). The module holds no logic of its own beyond shaping the operation payload.

Watch for: `value` is typed `string` only, so numeric, date, and checkbox cells must be stringified by callers with no declared round-trip contract (confirmed); positional `row: number` addressing is safe only if the revision precondition covers whole-table row order (possible — needs a check of what revision the table resource stamps); no test file accompanies this module (confirmed); the header comment presents concurrency as solved when the actual behavior is that a concurrent edit to a *different* cell now fails the precondition, and no retry or merge path exists here (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The value contract is the weak point. A smart table has typed columns — number, date, checkbox, select — but the signature admits only `string`. Either the write verb canonicalizes strings back into typed cells, in which case that coercion is the real contract and belongs where it can be tested, or callers stringify and cell type fidelity depends on each call site.

Row addressing is positional. Combined with a table-wide revision this is coherent; combined with a per-row or per-cell revision it is a stale-index hazard, since an insert above the target shifts the row a caller read. Which one applies is not visible in this file.

The failure mode changed rather than disappeared. Two people editing different cells previously produced silent loss; now the second write is rejected. That is the better failure, but nothing in this module or its documented contract tells a caller to re-read and retry, and the header comment reads as though the conflict were resolved.

<details>
<summary>Issues (5)</summary>

1. **String-only cell value** — `value: string` cannot express number, date, or checkbox cells without caller-side stringification; declare a typed cell value union or document where coercion happens and test it.
2. **Positional row addressing** — `row: number` is an index; confirm the revision precondition is table-wide (so an insert invalidates it) and state that invariant, otherwise switch to a stable row identifier.
3. **No conflict-recovery contract** — the revision precondition converts silent loss into a rejected write, but no re-read/retry guidance or helper exists; the caller is left to discover this.
4. **Missing tests** — no `table-write.test.ts` in this change; add coverage for ref construction and the `set_cell` payload shape, which is exactly the kind of field-name drift that only surfaces at the gate.
5. **No input guards** — empty `path`, empty `field`, and negative or non-integer `row` are forwarded to the gate unchecked; reject them locally or state that validation is deliberately server-side.

</details>

### Payload shape is unpinned

```ts
export async function setTableCell(
  path: string,
  row: number,
  field: string,
  value: string,
): Promise<RecordWriteResult> {
  return writeRecord(tableResourceRef(path), (expected_revision) => ({
    kind: 'set_cell',
    expected_revision,
    row,
    field,
    value,
  }));
}
```

The operation is an inline object literal with a `kind` string. If `writeRecord`'s callback return type is a discriminated union over operation kinds, a typo in `kind` or a missing field fails to compile; if it is loose (`Record<string, unknown>` or similar), the payload contract drifts silently until the gate rejects it — the same class of failure as the historical `content` vs `body` mismatch. This file alone does not establish which holds, and no test pins the payload.

The snake_case `expected_revision` inside a camelCase module is presumably deliberate wire alignment with the Rust serde contract; worth keeping consistent across all operation payloads so it reads as a boundary rather than a slip.

### What the precondition buys

Conflict granularity is determined entirely by whatever revision the table resource stamps, not here. This module cannot let two distinct-cell edits both succeed, and cannot tell that a rejected write was in fact non-conflicting. For a single-user local product that is an acceptable trade, but the header comment overstates it: what was gained is a truthful reply about whether the write landed, not merged concurrent edits.
