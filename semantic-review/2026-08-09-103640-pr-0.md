# Canonical task Resource and the shared record-write reply shapes

Two new kernel files. `task_resource.rs` makes a note's task list a Resource at `ctrl://local/task/<note>` whose only write is one bounded field change on one checkbox line, staged before approval, conditioned on the note's content revision, committed through the existing `tasks_source::update` writer, then reread before any success is reported. `record_write.rs` holds the three replies all record owners share — stale precondition, unverified write, rolled-back write — plus the empty-field display rule and the request/result schemas, so tasks, calendar events, and table cells cannot drift into three different-looking failures. The per-note lock comes from the process-wide `vault_write_lock` registry, so the canonical write serializes against the legacy bespoke vault writers on the same file.

Watch for: the write contract's clause 3 recovery point does not exist — the previous content is held only in memory, and the `rollback_failed` reply therefore cannot name a recovery location (confirmed); the rollback restores through `vault::write`, which re-emits the frontmatter from parsed JSON and so does not put the note back as it was read, contradicting the comment on the field it restores from (confirmed); and verification compares the requested literal against the parsed value, so any input the delegated writer normalizes — `tags` with two tags or a `#` prefix, `status` as `x`/`complete`/`completed` — is written, then rolled back, and reported to the caller as a failure (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

`produce` takes the per-note guard from the shared registry before the recheck read and holds it across the delegated write, the reread, and the rollback, keyed on the same vault-relative path the note owner and the bespoke `mcp_server` writers use — so recheck-to-reread is one critical section and a legacy write on the same note cannot interleave. Clause 7 holds.

Clause 3 does not. The reference note owner writes the previous bytes to a durable recovery point outside the content tree before mutating, and names that location when restoration fails. Here the previous content lives in `OpenedTasks.content` in memory, and the field's doc comment cites clauses 3/6 for it. A crash between the delegated write and the reread leaves nothing to recover from, and the `rollback_failed` reply carries only `expected`/`observed`, so the non-retryable failure the contract requires to be hand-recoverable tells the user nothing about where the old content went.

The rollback also does not restore what was read. It calls `vault::write` with the parsed `frontmatter` value, which re-emits the block from JSON — frontmatter comments are dropped and a note that had no frontmatter gains an empty `---\n---` block. The comment on the stored content says "The note exactly as it was read. Held so a write that does not verify can be undone"; the test in the same file quietly acknowledges the mismatch by comparing content instead of bytes.

Verification is stricter than the writer it verifies. `field_value` renders the parsed task, `expected` is the caller's trimmed request, and they are compared directly with one special case for status casing. Every other normalization the writer performs — comma-splitting and `#`-stripping tags, mapping `x`/`complete`/`completed` to `done` — reads back as a mismatch, so a legitimate write is applied, rolled back, and reported as `write_rolled_back` with `retryable: true`. `tags` is advertised in `FIELDS` and the descriptor schema but is only writable as a single bare tag.

A successful write is also wider than the descriptor's "one bounded field change on one task line". Because the delegated writer rebuilds the whole body from `lines()` and writes through `vault::write`, a plain note gains an empty frontmatter block and a CRLF note is rewritten with LF endings throughout — and the reread only checks the changed field, so both are reported as verified successes.

<details>
<summary>Issues (5)</summary>

1. **Missing write recovery point (clause 3)** — the previous content is held only in memory, so a crash between commit and reread is unrecoverable and `rollback_failed` cannot name a recovery location. Capture the previous bytes under the kernel derivative state root before delegating the write, abort if that capture fails, and put its path in the `rollback_failed` details.
2. **Rollback is not a faithful restore** — `vault::write` re-emits frontmatter from parsed JSON (comments lost; a plain note gains `---\n---`), so the comment claiming the note is put back "exactly as it was read" overstates the code. Restore raw bytes (a recovery point plus the atomic writer, or `write_body` semantics), or state the actual guarantee.
3. **Normalized values can never verify** — `tags` with more than one tag or a `#` prefix, and `status` as `x`/`complete`/`completed`, are written, rolled back, and reported as failures. Compare the reread against the normalized form the writer produces (or against a re-parse of the rendered line), not against the caller's raw string.
4. **A verified write changes more than the addressed line** — a plain note gains an empty frontmatter block and a CRLF note is converted to LF, yet the reread only checks the changed field and reports success. Either narrow the commit to the addressed line's bytes or verify that the untouched region is unchanged before claiming success.
5. **`tags` advertised as writable while effectively unusable** — the descriptor's `value` is a bare string with no statement of the comma-separated, `#`-less form the writer expects. Until issue 3 is fixed, constrain or document the accepted shape in the operation schema rather than letting a plausible input read back as a conflict.

</details>

<details>
<summary>Details</summary>

### Recovery point exists only in memory

`OpenedTasks.content` carries the doc comment "Held so a write that does not verify can be undone instead of leaving the note holding a value nobody asked for. (ADR-002 substrate §15.2 v87 clauses 3/6)". Clause 3 is specifically about durability: "The previous bytes are durably captured outside the user's content tree, beneath the kernel-managed derivative state root, before the file is modified. A recovery point that cannot be written aborts the operation." Nothing is written before `tasks_source::update` runs, and the abort-on-failure branch has no code to be in.

The consequence shows up in clause 6's failure half. `record_write::write_rolled_back` builds the `rollback_failed` reply from `expected` and `observed` only:

```rust
feedback.code = "rollback_failed".to_owned();
feedback.message =
    "the change did not read back with the new value and the previous content could not be restored"
        .to_owned();
feedback.retryable = false;
```

The reference note owner puts `recovery_point` in the details for exactly this case. Here the caller is told the note holds something nobody asked for and that retrying will not help, with no way to reach the previous content. Same for a crash: the only copy of the pre-write content is a `String` on the stack.

### The restore path rewrites the frontmatter block

Rollback goes through the vault writer with the parsed frontmatter:

```rust
let restored = super::vault::write(
    self.root()?,
    &note,
    &opened.content,
    &opened.frontmatter,
)
.is_ok();
```

`vault::write` renders the block as `format!("---\n{yaml}---\n\n{content}")` from `frontmatter_to_yaml`, so what comes back is a re-serialization of the parsed value, not the original bytes. A note whose frontmatter carried an inline comment loses it on rollback; a note with no frontmatter gains `---\n---\n\n`. ADR-002 records this same property as the reason `vault_doc` uses `write_body` instead ("`vault::write` would have errored on Null fm and alphabetized keys through the YAML→JSON→YAML round-trip").

### Verification is stricter than the writer

```rust
let verified = observed.is_some_and(|current| {
    let actual = Self::field_value(current, &field);
    actual == expected || (field == "status" && actual == expected.to_lowercase())
});
```

`expected` is `display(&value)` — the caller's string, trimmed. `actual` is the parsed task rendered back: `item.tags.join(" ")` for tags, the normalized status word for status. The delegated writer splits tags on commas and strips `#`, and maps `x`/`complete`/`completed` to `done`. So a `tags` write of `"work, home"` produces a task carrying `work home`, fails the comparison, is rolled back, and the caller receives `write_rolled_back` with `expected: "work, home"`, `observed: "work home"` — a conflict reply for a write that did exactly what was asked. Only a single tag with no `#` survives. The status special case covers casing but not the synonyms the writer accepts, and the descriptor schema puts no enum on `value`, so those synonyms are schema-valid input.

### A successful write is wider than one line

`tasks_source::update` rebuilds the body with `entry.content.lines()` and `join("\n")`, then writes through `vault::write`. Two effects survive the reread because it only inspects the changed field:

- a note with no frontmatter comes back with `---\n---\n\n` prepended;
- a note with CRLF line endings comes back entirely LF.

Both are reported with `effect.verified_by = "post-write reread returned the new value"`, which is true of the field and false of the file. The descriptor comment ("One bounded field change on one task line") and the module doc are what overstate here; the write itself is atomic, so this is fidelity rather than a partial apply.

### What is not tested

The reread-failure branch is unexercised (the ADR acceptance list already carries it as an open item needing filesystem injection). Beyond that: no test writes `tags` or a status synonym, so issue 3 is invisible to the suite; no test asserts the restored file's bytes, so issue 2 is only visible as the comment in `a_write_that_does_not_read_back_is_rolled_back_and_reported` explaining why it compares content instead; no test covers a note that already has frontmatter, on either the success or the rollback path; and the per-note lock is proven in `vault_write_lock`'s own tests rather than through two concurrent `produce` calls on one task list.
