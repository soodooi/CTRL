# First governed Markdown note write (`replace_content`)

`MarkdownNoteOwner` gains one bounded produce operation, `replace_content`, and the canonical `produce` gate path now stages the change and hands the staged Outcome facts to ReviewGate before asking a human. The six §15.2 v87 clauses all exist as real code — stage before authorization, revision recheck through a fresh stable handle, pre-write recovery point, flushed temp sibling + rename, post-write reread with `effect.verified_by`, and rollback-or-name-the-recovery-point on mismatch — and the twelve `note_resource` tests pass (`cargo test --lib note_resource`: 12/12). The ADR amendment and the generated pipeline artifact are honest about what is not done: U6/U10/U11 stay `partial` with the missing frontend caller and the un-adapted approval surface recorded as gaps.

Watch for: the recovery point lands **inside** the vault in both production constructors, contradicting clause 3 and the ADR text (confirmed); the atomic-commit step writes through a rebuilt path with `File::create`, which follows a pre-planted symlink at the temp sibling and steps outside the stable-handle discipline the read path enforces (confirmed); the recovery point is not fsynced, so "durably captured" is not established (confirmed); the canonical produce path takes no per-file lock while every legacy vault write verb does, so a concurrent write can be rolled back to a third revision while its author reports verified success (confirmed); and `stage` returns a placeholder ResourceRef on a stale revision, i.e. an Outcome naming a resource that does not exist (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The write contract is structurally right. Staging is a distinct owner method returning `Outcome`, the gate calls it before it asks for approval, and a missing stage stays missing rather than being replaced by an argument dump. Typed failure survives: a moved revision comes back as a serialized `Outcome` with `feedback.code = "precondition_failed"` and `retryable: true` rather than a transport error string, and the file is untouched.

Containment is where the slice is weakest. Reads go through `StableRoot`/`openat(O_NOFOLLOW)` and authorization observes the opened handle. The commit does not: `actual_path` rebuilds `root + id_segments` and the write goes through `std::fs::File::create` plus `rename`. Ref grammar blocks `.`/`..`/separators, so the rebuilt path cannot traverse out by construction, and the read immediately before proves the components were not symlinks at that instant — but `File::create` on the temp sibling has no `O_NOFOLLOW`/`O_EXCL`, so an already-present symlink at `.<name>.md.ctrl-tmp` redirects the content write outside the authorized root and leaves the note itself replaced by that symlink. The same rebuild reopens by name rather than by the verified handle identity, so the revision recheck and the mutation can, in principle, apply to two different objects.

The recovery point is in the wrong place in every production path. `new()` uses `<root>/.ctrl-recovery` and `from_default_vault()` uses `<vault>/.ctrl/recovery`; both are under the user's content tree, which clause 3 explicitly excludes. Only the test helper `with_recovery_root` puts it elsewhere, so the tests validate a configuration production never uses. Because the location is inside the vault and the segment validator permits dot-prefixed names, those copies are addressable as notes (`ctrl://local/note/.ctrl/recovery/<hash>.md`) and land in vault index/git scope. The recovery write is also a plain `fs::write` with no file or directory fsync, and its name is a fixed digest of the ref, so a second write for the same note overwrites the previous safety copy and nothing ever cleans them up.

Concurrency is unserialized. Every legacy vault write verb in `mcp_server.rs` acquires `vault_write_lock(path)`; the canonical produce path acquires nothing, and it does not even serialize against those legacy writers on the same file. Two produce calls that both observe revision A both pass the recheck; whichever rereads second sees the other's bytes, treats that as a verification mismatch, and restores its recovery point — reverting the file to A while the other caller has already reported a verified success. Clause 6's rollback machinery becomes the loss mechanism.

Review facts are gate-derived and cannot be fabricated: `ReviewRequest.outcome` is only ever `Outcome::review_facts()` from the owner's own `stage`, `None` when nothing staged, and the approve path is unchanged first-party command surface, so no-self-approval holds. The one fact defect is on the stale-revision branch, where `stage` returns `precondition_failed`'s hardcoded `ctrl://local/note/placeholder.md`; `produce` overwrites `resource` on that branch, `stage` does not.

Capability scope reaches the owner from the caller-supplied `X-Ctrl-Intent` header (`canonical_resource_context` uses a declared scope verbatim), so `authorize_context`'s `notes`/`vault` requirement is caller-asserted, and the `X-Ctrl-Caller` header decides `is_user_surface`, which decides whether review runs at all. Both are pre-existing mechanisms, but this is the first slice where they gate a real content mutation, and §17.4 does not record that the owner-side scope is self-declared.

<details>
<summary>Issues (7)</summary>

1. **Recovery point inside the user's content tree** (confirmed) — `new()` → `<root>/.ctrl-recovery`, `from_default_vault()` → `<vault>/.ctrl/recovery`. Clause 3 requires the kernel-managed derivative state root; move both to it (e.g. under the app state dir) and cover the production constructors, not only `with_recovery_root`.
2. **Temp sibling follows a pre-planted symlink** (confirmed) — `File::create(".<name>.md.ctrl-tmp")` has no `O_NOFOLLOW`/`O_EXCL`, so an existing symlink there sends content outside the authorized root and `rename` leaves the note as that symlink. Create the temp file with `openat` on the verified parent directory handle using `O_NOFOLLOW | O_EXCL` and a unique suffix, then `renameat`.
3. **Commit reopens by path instead of the verified handle** (confirmed) — `actual_path` rebuilds `root + segments`; grammar prevents traversal but the mutation is not bound to the object whose revision was just rechecked. Carry the parent directory handle from the recheck into the commit so clause 2's recheck and clause 4's commit provably act on one object.
4. **Recovery point is not durable** (confirmed) — `fs::write` with no `sync_all` and no parent-directory fsync; clause 3 says durably captured. Flush the recovery file and its directory before mutating the note.
5. **No write serialization on the canonical path** (confirmed) — legacy vault verbs take `vault_write_lock`, `produce` takes nothing. Concurrent writers can pass the revision recheck together and the loser's rollback reverts the winner's committed content while the winner reports verified success. Hold the same per-path lock across recheck → recovery → commit → reread.
6. **Fixed recovery filename, no retention** (confirmed) — one `<sha256(ref)>.md` per resource, overwritten by the next write and never cleaned up. Make each recovery point distinct per operation and define its retention.
7. **Placeholder ResourceRef in a staged failure Outcome** (confirmed) — `stage` returns `precondition_failed`'s `ctrl://local/note/placeholder.md` unmodified, so a typed failure names a resource that does not exist; §15.5 forbids non-owner facts. Set `resource` from the addressed ref on that branch as `produce` already does.

### Clause-by-clause status

Clause 1 (stage before authorization) — `ResourceOwner::stage` is a separate method; `MarkdownNoteOwner::stage` authorizes context, parses the bounded operation, reads through the stable handle, compares `expected_revision`, and returns an `Outcome` carrying `target`, `staged.before/after` (2000-byte previews) and a `Revision` precondition. `mcp_server::produce` calls `prepared.review_facts(&context)` before `request_with_outcome`. The test asserts the file is unchanged after staging.

Clause 2 (recheck through a fresh handle) — `produce` calls `self.read(resource)` again, which opens a new `StableRoot` and `open_beneath`, then compares. On mismatch it returns a serialized `Outcome` with typed retryable `Feedback` and no `effect`. The mismatch path is tested including "external edit survives".

Clause 3 (recovery point) — present and abort-on-failure is tested (`an_unwritable_recovery_point_aborts_before_mutating`), but the location and durability are wrong as described above.

Clause 4 (atomic commit) — `commit_atomically` writes a `.ctrl-tmp` sibling, `write_all`, `sync_all`, `rename`, and removes the temp on rename failure. The flush-and-rename shape is correct; the file creation is the unsafe part.

Clause 5 (post-write reread) — re-reads through `read`, compares against `sha256(new content)`, and only then sets `effect.verified_by = "post-write reread matched the expected revision"`. `is_verified_success()` is asserted, though only under `debug_assert!`.

Clause 6 (partial failure) — on mismatch it reads the recovery point and re-commits it, reporting `write_rolled_back` (retryable) or, when restoration fails, `rollback_failed` (non-retryable) with the recovery path in `details`. Note this is the one place the owner deliberately emits a filesystem path; that is what the clause asks for, but it means an unapproved caller learns a kernel path on that branch.

### Write-without-scope, without staging, or on a stale revision

Stale revision is closed on both paths. Scope is enforced in every verb via `authorize_context`, with a test proving a `registry`-scoped caller is denied and the file untouched — the caveat is that the scope value itself is caller-declared.

Staging is not structurally required: `produce` never consults `stage`, and the review branch is skipped entirely when `is_user_surface(caller)` or when `ReviewGate::enforcing()` is false. The invariants staging checks are re-checked inside `produce`, so this is not a correctness hole, but the tool description "Every supported call passes through ReviewGate" is not accurate for `pwa`/`irisy` callers.

### Honest status

`vault/ctrl/generated/pipeline-conformance.json` reports U6/U10/U11 as `partial` with `failingStages: ["declaredGaps"]`, and names the real gaps: no frontend surface invokes the write, the approval adapter does not read `request.outcome` yet, only whole-note replacement is in scope, and legacy string-flattened tools still reach the gate without facts. Domains report 19 verified / 1 partial. Nothing here claims the vertical is user-served. The one wording stretch is the ADR v87 changelog's "Lights ADR-005 §12 U6/U10/U11 pipelines with real evidence rather than declarations" — the artifact shows those pipelines moved from declared to partial, not lit. The substantive ADR/code drift is clause 3's "outside the user's content tree" versus both production constructors.
