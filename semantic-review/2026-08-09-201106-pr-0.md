# Atomic vault writes, raw read/restore, and CRLF frontmatter fixes

`vault.rs` gains a single `write_atomically` helper (flushed temp sibling + `rename`) now backing both `write` and `write_body`, replacing the truncating `fs::write` that could leave a half-written note. It adds `read_raw`/`restore_raw` so the Resource owners (`task_resource`, `table_resource`, `calendar_resource`) can capture a note's exact bytes and put them back verbatim when a post-write reread fails. Two CRLF bugs are fixed: the opening fence is now measured as 5 bytes on a CRLF note rather than 4, and the fence/body separator is stripped as a single character class instead of `\n`-then-`\r`, which had left CRLF notes holding `\n\r\n`. `write_body` also emits the note's own terminator for the separator.

The CRLF fixes are correct for all three cases asked about. The write half is weaker than the sibling implementation already in the tree: `note_resource::commit` performs the same temp-then-rename with `O_EXCL | O_NOFOLLOW`, a nanosecond-unique staging name, and a parent-directory fsync, and `write_atomically` has none of those.

**Watch for:** `write_atomically` uses a *predictable* staging name opened with `fs::File::create`, which follows symlinks — a pre-planted `.<note>.ctrl-tmp` link writes note content outside the vault and leaves the note itself a symlink (**confirmed**, reproduced). `restore_raw` reverts the bytes on disk but is the only raw-bytes writer that does not refresh the FTS index, so a rollback leaves the index holding the failed write's content (**confirmed**). `write_body` infers its terminator from `raw.contains("\r\n")` over the whole file, so an LF note with one CRLF line in its body gets a rewritten closing-fence line (**confirmed**). No parent-directory fsync, so the rename is not durable across a crash despite the docstring's claim (**confirmed**). Replace-by-rename widens a `chmod 600` note to `644` and breaks hardlinks (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

Consolidating every vault write behind one helper is the right move; what is missing is everything that makes replace-by-rename safe at a path an untrusted party can also write to. `note_resource.rs` in this same tree already worked that out — `O_NOFOLLOW` so the staging name cannot redirect the write, `create_new` so a colliding writer fails instead of sharing the file, a unique staging component, and a directory fsync after the rename. `write_atomically` uses a fixed `.{file_name}.ctrl-tmp` and plain `File::create`, so it inherits none of it, and its failure cleanup unconditionally unlinks that shared path — the exact deletion `note_resource` orders itself to avoid.

The CRLF work holds for empty frontmatter, leading whitespace before the fence, and a CRLF body that must not absorb a stray `-`, and the prefix and split halves agree on their boundaries. A note with no closing fence still makes `write_body` drop the fence-like text — unchanged from the base branch and out of scope, but the diff rewrites the function that decides it.

`restore_raw` validates its path through the same `sanitize_relative_path` as every other writer, so the containment question asked about is answered. What it does not share is the writers' index posture: `write`, `write_body`, and the `refresh_index_for` helper used by the notes-ui adapter all update FTS and flag embeddings; `restore_raw` updates neither, so the rollback path ends with disk and index disagreeing.

The separator terminator fix trades one asymmetry for its mirror. Sourcing the terminator from the whole file rather than from the fence means the LF-note-with-CRLF-body case now gets exactly the byte change the comment says it is avoiding.

<summary>Issues (6)</summary>

1. **Symlink escape via predictable staging name** — `fs::File::create` on the fixed `.{file_name}.ctrl-tmp` follows a pre-planted symlink, writing note content outside the vault and leaving the note a symlink to that path. Open with `create_new(true)` + `custom_flags(libc::O_NOFOLLOW)` and a unique staging component, as `note_resource::commit` does.
2. **Shared staging name collides between writers** — two concurrent `write_atomically` calls on one note truncate each other's staging file, and the error path unlinks a path another writer may own. `create_new` + a unique name makes a collision fail instead of interleave.
3. **Rollback leaves the FTS index stale** — `restore_raw` reverts disk bytes but never calls `refresh_index_for`, so after a rolled-back write the index and embeddings still hold the failed write's content. Refresh from the restored bytes.
4. **`write_body` terminator inferred from the whole file** — `raw.contains("\r\n")` makes an LF note with a single CRLF body line get a CRLF closing-fence line. Derive the terminator from the fence itself.
5. **No parent-directory fsync** — `sync_all` on the file does not make the rename durable; a crash can lose the committed note despite the docstring's crash-safety claim. Fsync the parent after the rename, or soften the claim to the (real) torn-read guarantee.
6. **Replace-by-rename widens permissions and breaks hardlinks** — a `chmod 600` note comes back `644` after the next write, and a hardlinked alias silently stops tracking the note. Carry the previous mode onto the staging file before renaming.

### The staging name is the vault's weakest write path

`write_atomically` derives its staging path deterministically and opens it with `fs::File::create`:

```rust
let temporary = parent.join(format!(".{file_name}.ctrl-tmp"));
let commit = || -> std::io::Result<()> {
    {
        let mut handle = fs::File::create(&temporary)?;
```

`File::create` is `O_WRONLY | O_CREAT | O_TRUNC` with no `O_NOFOLLOW`, so if that path is a symlink the open resolves it and the write lands on the target. Both halves of the name are derivable from the note path alone. Planting a link at `.budget.md.ctrl-tmp` and then triggering any write to `notes/budget.md`:

```
write_atomically -> Ok(())
outside file now = Ok("---\ntitle: Secret\n---\n\nsecret body\n")
note is symlink  = Ok(true)
note reads as    = Ok("---\ntitle: Secret\n---\n\nsecret body\n")
```

The note's bytes were written through the link to a path outside the vault, and the `rename` then moved the link itself onto `budget.md` — so the note *is* now a symlink pointing outside the root, and every subsequent write follows it. The call reports `Ok(())` throughout.

This is the case `note_resource.rs` already defends, with a test that plants a link at the identical `.note.md.ctrl-tmp` name, and the reason its comment reads "a pre-planted symlink or file at the staging name must not redirect the write outside the authorized root". `resource_fs.rs` carries a `SymlinkRejected` variant and rejects links at root, intermediate, and final components. `write_atomically` is the one vault writer that opts out of that discipline, and it is the one every `vault::write` and `vault::write_body` caller goes through.

The fixed name is also why concurrent writers interact badly. `File::create` truncates rather than failing, so two writers on one note share a staging file and the rename commits whatever interleaving won. The cleanup compounds it:

```rust
commit().map_err(|error| {
    let _ = fs::remove_file(&temporary);
```

On any failure this unlinks a path that, under a fixed name, may be a *different* writer's staging file — the deletion `note_resource` explicitly sequences around ("cleaning up before a successful create would delete a file another writer owns"). The per-path lock in `vault_write_lock` covers the Resource owners and the gate, but `vault::write` has many callers that do not take it, and `commands/notes_ui.rs` writes vault files with plain `fs::write` outside the registry entirely.

### The CRLF fixes hold, including the cases asked about

Both halves now measure the opener the same way, and the separator strip handles `\r\n\r\n` in one pass. Probing the parsers directly:

```
empty fm CRLF   "---\r\n---"                    prefix "---\r\n---"           body ""
empty fm + body "---\r\n---\r\n\r\nBody.\r\n"   fm ""                          body "Body.\r\n"
CRLF fm + body  "---\r\ntitle: X\r\n---\r\n..." prefix "---\r\ntitle: X\r\n---" body "Body.\r\n"
lead blanks     "\r\n\r\n---\r\ntitle: X\r\n---\r\n\r\nBody.\r\n"              body "Body.\r\n"
lead spaces     "  \n---\ntitle: X\n---\n\nBody.\n"                            body "Body.\n"
```

Empty CRLF frontmatter takes the `after_open.starts_with("---")` branch, which is offset-independent, so it was never affected. Leading whitespace works because `raw_frontmatter_prefix` keeps `lead` in its final slice (`&raw[..lead + opener + body_start]`) while `split_frontmatter` computes offsets against `trimmed` and never mixes the two — that `lead` term is what keeps the two halves agreeing.

A note with **no closing fence** returns `""` from `raw_frontmatter_prefix`, which sends `write_body` down its `prefix.is_empty()` branch and replaces the whole file with the body — the unterminated fence and its keys are dropped. Identical on the base branch, so not a regression, but the diff rewrites the deciding function and adds no coverage for it.

### The rollback path ends with disk and index disagreeing

`restore_raw` is the recovery half of the §15.2 clause 6 contract, called by all three Resource owners when a post-write reread does not verify:

```rust
let restored = super::vault::restore_raw(self.root()?, &note, &opened.raw).is_ok();
```

The write it is undoing went through `tasks_source::update` → `vault::write_body`, which upserts FTS with the *new* body and flags embeddings stale. `restore_raw` writes the old bytes and stops; `refresh_index_for` — the helper that exists specifically for callers writing raw bytes themselves, used by the notes-ui adapter and `rewrite_wikilinks` — is never called. After a rolled-back task write, search and semantic lookup still reflect content that is no longer on disk. The FTS upsert is `#[cfg(not(test))]`, so no unit test can observe this.

### The terminator fix reintroduces its own mirror

```rust
let terminator = if raw.contains("\r\n") { "\r\n" } else { "\n" };
format!("{prefix}{terminator}{terminator}{body}")
```

The scan is over the entire file, not the fence. An LF-framed note with one CRLF line anywhere in its body picks `\r\n`:

```
in   "---\ntitle: X\n---\n\nline1\r\nline2\n"
out  "---\ntitle: X\n---\r\n\r\nNEW"
```

The prefix ends at the closing `---` without its terminator, so the two appended terminators *are* the fence's line ending — the note's frontmatter block now ends CRLF where it ended LF, on a call whose contract is that frontmatter bytes survive verbatim. It round-trips through `read`, so nothing breaks downstream; it surfaces as a spurious frontmatter change in the user's git diff, the same complaint the comment above it is answering. Deriving it from the fence (whether the matched opener was `---\r\n`, or the two bytes preceding the closing fence) covers both directions.

### Durability and file identity

The docstring claims the flush ordering makes the atomic-commit clause true, but `sync_all` on the staging file only gets the *content* to disk; the directory entry the `rename` creates is itself unsynced, so a crash shortly after can leave the old note. The torn-read guarantee ("a reader sees either the old note or the new one") is real and is the main point; the crash-durability claim is not, without an fsync on the parent. `note_resource::commit` does this immediately after its rename.

Replacing the inode rather than truncating it also drops properties of the file the user may have set:

```
fs::write         private note mode after rewrite = 600
write_atomically  private note mode after rewrite = 644
hardlink alias sees = "v1" (target = "v2")
```

A note the user restricted comes back world-readable. Carrying the previous mode onto the staging file before the rename keeps this a pure content replace. The hardlink divergence is inherent to replace-by-rename and probably acceptable, but it is a behavior change for anyone linking notes into a vault.

### Test coverage

The three new tests assert on observable consequences rather than implementation — no temp sibling survives a write or gets listed as a note, a CRLF note keeps its frontmatter across a body rewrite, and `split_frontmatter` on a CRLF note yields the right first line and line count, which is the assertion that matters given line indices are what task and doc writes address. All 26 tests in the module pass.

Not tested: a symlink at the staging name (the case `note_resource` does cover, and the one that escapes the vault); two writers racing one note; the index state after `restore_raw`; `restore_raw` and `read_raw` at all, in either direction, including the round-trip that a note with comments and hand-ordered keys comes back byte-identical; an LF note with CRLF in its body; a note with no closing fence; permission preservation.

### Unrelated changes in the same diff

Roughly half the line count is `cargo fmt` reflow of untouched code — `walk_markdown`'s signature, `patch_frontmatter_key`'s closure, `rewrite_wikilinks`'s `stem_of`, a let-else, and a dozen test-body reformats. It inflates a ~120-line behavioral change to 294 and buries the parts worth reading.
