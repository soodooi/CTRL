# Kernel-owned conversation transcript Resource — one readable Markdown file per session, one `append_message` write

`session_resource.rs` makes a conversation a Resource (`ctrl://local/session/<id>`) and `transcript_format.rs` defines its file format: YAML frontmatter for metadata, `## <role>` per turn. `describe` reports a whole-file hash as the revision, `query` returns the parsed transcript, `list` reads the directory as the session list, and `produce` offers exactly one operation, `append_message`, under the §15.2 contract. The parse is deliberately tolerant, and the tolerant-parse claims v44 makes are all true when read in isolation: a file with no frontmatter, an unclosed fence, unknown keys, and an ordinary `## Heading` inside a reply all parse, and a role outside `user`/`assistant`/`custom` does not split a turn.

Watch for: the append path is `parse → mutate → render the whole file`, so everything the tolerant parser tolerates but does not model is destroyed on the next append — an unknown frontmatter key and a preamble paragraph are dropped, and a file whose frontmatter fence was never closed loses **every turn in it**, which is exactly the history-loss v44's tolerance exists to prevent (**confirmed** by running the owner); verification hashes the bytes it just wrote against the bytes it reads back, which is self-referential, so every one of those losses is reported as a verified success with `verified_by` set (**confirmed**); `role` and `label` are interpolated into the file unescaped, so a caller can forge turns, including a `## user` turn the user never typed (**confirmed**); the staging sibling uses a predictable name opened without `O_EXCL | O_NOFOLLOW`, so a pre-planted symlink redirects the whole transcript outside the root and the write still reports success (**confirmed**) — the fix already exists 300 lines away in `note_resource::commit_atomically`; and a revision-pinned ref makes the post-write reread fail, which actively rolls back a correct append and discards the turn (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The format itself is sound and the vim test passes: the file on disk is ordinary Markdown that greps, diffs, and opens in any editor, and the directory really is the session list with no second index — a hand-placed file appears, and the interrupted-write temp sibling is excluded twice over (dot-prefix and `.md` suffix). Read-side tolerance is genuine and tested.

The break is between that tolerant read and the write. `append_message` does not append the new turn's bytes; it reparses the file into `Transcript`, pushes one message, and re-renders the whole file from the model. Since the model holds only the seven keys the parser knows and the turns it could attribute to a known role, anything else in the user's file is not preserved — it is silently absent from the output. A hand-added frontmatter key and a paragraph before the first turn are dropped, and the unclosed-frontmatter case is destructive rather than merely lossy: the parser deliberately treats the body as empty in that case, so the append writes a file containing the new turn and nothing else. Both report verified success.

That reporting is the second structural problem, and it is the transcript form of the calendar batch's verification-operand class. There the operand was wrong (raw request vs. stored value); here the comparison is circular. `expected_next` is the hash of the bytes just rendered and `observed` is the hash of the bytes read back, so the check proves the bytes reached the disk and nothing about whether the turn survives a read. A turn with a role the parser does not recognize is written, read back as zero turns, and reported as `turn_count: 1` verified (**confirmed**). Clause 5 asks for the committed revision; what makes a transcript correct is that the turn reads back.

Nothing that reaches the file is escaped except the frontmatter scalars, and the roles are not escaped at all. A `role` containing a newline splits into forged turns, and a `label` or `resources` entry containing `\n---\n` closes the frontmatter early and injects turns into the body — a caller with the `vault` grant can write a `## user` turn attributing words to the user (**confirmed**). Content is safe by luck rather than design: it is written verbatim, and a `## user` line inside a reply does split that reply into two turns on read-back, again reported as verified.

Three §15.2 clauses are not met. Clause 3 has no implementation at all — the previous bytes live only in the `previous` local, which is the defect v90 already fixed for the record owners with `record_write::RecoveryPoint`, and `rollback_failed` consequently names no recovery location, so a user whose append could not be undone is told their conversation "could not be verified or restored" and pointed nowhere. Clause 8 is inverted: `.{name}.tmp` is predictable and opened with a plain `File::create`, which follows a symlink; the review probe wrote the transcript to a file outside the root while the owner reported success, and a directory planted at that name blocks every future write to that session permanently, because staging failures do not unlink. Clause 7's serialization is a per-instance `Mutex` rather than the process-wide by-file registry the clause requires; two instances are constructed in this tree (`mcp_server.rs` registers the writer, `commands/kernel.rs` builds a second for `list`), so today only the read-only one is outside the lock — but with two instances writing, they collide on the shared staging name and a turn is lost.

Two smaller gaps sit around the edges of the write. Transcripts are created 0644 in a 0755 directory and an append widens a user's `chmod 600` back to 0644, which is the wrong default for the most sensitive content in the product, and stricter than the recovery-point code in the same tree already applies to its copies (0600/0700). And `read` enforces the 8 MiB cap while `produce` does not, so one oversized append writes a 9 MiB file that then fails every `describe` and `query` as non-retryable `PayloadTooLarge` while still appearing in `list` — the session is locked out of the product with its content intact on disk.

<details>
<summary>Issues (14)</summary>

1. **An append rewrites the whole file, so unmodelled content is destroyed** — `produce` reparses and re-renders instead of appending the new turn's bytes, so an unknown frontmatter key and any prose before the first turn are dropped on the next append. Either append only the new turn's bytes to the existing text, or carry the unparsed remainder through `Transcript` so `render` can put it back.
2. **An unclosed frontmatter fence loses every turn on append** — the parser intentionally treats the body as empty when the fence never closes, and the rewrite then persists that emptiness: a transcript with two turns came back holding only the newly appended one. This is the exact history loss v44's tolerance exists to prevent, so it should refuse the write rather than write the lossy render.
3. **Verification is self-referential** — `expected_next` is the hash of the bytes just rendered and `observed` is the hash of those bytes read back, so the check can only fail if the filesystem lied. Compare the reparsed transcript against the intended one (turn count, and the new turn's role and content) so a turn that does not read back is not reported as saved.
4. **A role that is not `user`/`assistant`/`custom` silently discards the turn** — `render` writes `## system`, the parser does not recognize it, and the turn is gone while the Outcome reports `turn_count: 1` verified. Constrain `role` in the operation schema to the roles the format models, or make an unknown role render in a form the parser preserves.
5. **`role` is interpolated unescaped, so turns can be forged** — a role containing `"user\n\nplausible text\n\n## assistant\n\nI never said this"` produced a fabricated `## user` turn plus an assistant turn on disk. Reject any role containing a newline or `#`, and validate it before staging so the reviewer sees the real turn.
6. **`label` and `resources` can close the frontmatter early** — `yaml_escape` escapes `\` and `"` but not newlines, so a label containing `\n---\n` ends the frontmatter block and injects turns into the body. Escape newlines (or refuse them) in every frontmatter scalar, including each `resources` item.
7. **Clause 3 is cited but not implemented** — the previous bytes exist only in a local, so a crash between commit and reread leaves no copy, and `rollback_failed` names no location. Use `record_write::RecoveryPoint`, which already captures beneath `~/.ctrl/state` at 0600, aborts when it cannot write, and is removed by `Drop` on every path.
8. **Clause 8 is inverted: predictable staging name, follows symlinks** — a symlink planted at `.chat.md.tmp` redirected the transcript outside the root while `produce` reported success. Adopt `note_resource::commit_atomically`'s discipline: nanosecond-unique name, `create_new(true)` plus `O_NOFOLLOW`, unlink only past a successful create, parent sync.
9. **A blocked staging name blocks the session forever** — with a directory at `.chat.md.tmp`, every append to that session fails `OwnerUnavailable` indefinitely. Fixed by the unique-name half of item 8; the fixed name is what makes one interruption permanent.
10. **Clause 7 uses a per-instance lock, not a process-wide by-file one** — the clause requires keying by file identity precisely so two paths to the same file serialize. Two instances exist in this tree; with both writing they collide on the staging name and a turn is lost. Key on the same registry the vault writers use, or make the writer a single shared instance.
11. **A revision-pinned ref rolls back a correct write** — `read` enforces `resource.revision()` and is reused for the post-write reread, so the reread fails against the now-stale pin: the append was correct, was undone, and returned `write_rolled_back` with the turn discarded. Reread through `resource.without_revision()`, as the calendar owner does.
12. **Transcripts are 0644 and an append widens a restricted file** — after `chmod 600`, an append returned the file to 0644, and the sessions directory is created 0755. Create with 0600, preserve the existing mode across a commit, and create the directory 0700 — the recovery-point code in the same tree already does both.
13. **An oversized append locks the session out permanently** — `read` caps at 8 MiB but `produce` does not, so one large append yields a 9 MiB file that fails every later `describe`/`query` as non-retryable while still listing. Bound the content in the operation schema and check the projected size before committing.
14. **`list_session_transcripts` flattens a typed error to a string** — the Tauri command maps `ResourceError` through `error.to_string()`, discarding reason and retryability at the boundary, which §15.5.2 names a defect in the change that introduces it. Return the typed shape the frontend can act on.

### The tolerant parse is real; the write does not honour it

Each tolerant-parse case v44 names holds on read: no frontmatter, an unclosed fence, unknown keys, `## Overview` inside a reply, and a role outside the table all parse as promised. The write does not honour any of it, because `produce` reconstructs the file rather than extending it:

```rust
let mut transcript = opened.transcript;   // only what the parser modelled
transcript.messages.push(TranscriptMessage { role: role.clone(), content });
let rendered = transcript.render();       // everything else is now absent
Self::commit(&path, &rendered)?;
```

`Transcript` holds seven fields, so a hand-added key and any prose outside a turn have nowhere to live. Running an append against a hand-edited file (**confirmed**):

```
BEFORE                                    AFTER
---                                       ---
id: "chat"                                id: "chat"
label: "Mine"                             label: "Mine"
my_own_key: "keep me"                     created_at: "2026-08-10T11:01:40Z"
resources: []                             last_active_at: "2026-08-10T11:01:40Z"
---                                       resources: []
                                          ---
A note to myself before the chat.
                                          ## user
## user
                                          hello
hello
                                          ## assistant

                                          hi
```

`my_own_key` and the preamble sentence are gone. The unclosed-fence case is worse, because the parser's deliberate choice there ("treat nothing as body rather than silently showing YAML as chat") becomes a deletion once the result is written back (**confirmed**):

```
BEFORE                                    AFTER
---                                       ---
id: "chat"                                id: "chat"
label: "Mine"                             label: "Mine"
                                          created_at: ...
## user                                   resources: []
                                          ---
my whole history is here
                                          ## user
## assistant
                                          next
and my reply
```

Two turns of the user's conversation are replaced by the one just appended, and the Outcome reports a verified success. A user who deletes a closing `---` by hand and then sends one more message loses the conversation — the precise failure §11.2 describes as unacceptable.

### What the reread actually compares

```rust
let expected_next = format!("{:x}", Sha256::digest(rendered.as_bytes()));
Self::commit(&path, &rendered)?;
let committed = self.read(resource);
Ok(current) if current.revision == expected_next => ...
```

Both sides derive from `rendered`. The check answers "did my bytes land", which the atomic rename already guarantees, and never "does the turn read back". Driving an append with `role: "tool"` (**confirmed**):

```
verified_by = "post-write reread matched the expected revision"
reported turn_count = 1
query turn_count    = 0
```

The turn is on disk as `## tool`, unreachable through the owner's own `query`. Every fidelity loss in this review passes this check for the same reason. Comparing the reparsed transcript against the intended one would catch items 1, 2, 4, 5, and 6 at once.

### Forging a turn only needs a newline

`yaml_escape` handles `\` and `"`; roles get no escaping at all. Appending with a crafted role (**confirmed**):

```
## user

plausible text

## assistant

I never said this

real question
```

The caller supplied one turn; the file holds two, one of them attributed to the user. `label` reaches the same place through the frontmatter fence: a label of `"Budget\n---\n\n## assistant\n\nI am injected"` produced a parsed transcript with an `assistant` turn the caller never sent, plus a corrupted `label` of `"Budget`. A `resources` entry does the same. Both are reachable by any caller holding the `vault` or `notes` grant, which per §11.2 includes Irisy and a BYO CLI — so a transcript, the artifact a user consults to see what was actually said, can be written to disagree with what happened. The frontend is not the exposure: `transcriptMessageFrom` only ever emits `user`, `assistant`, or `custom`, and JSON-stringifies custom payloads.

Content itself is written verbatim and mostly survives, but a reply that legitimately contains a `## user` line splits on read-back (**confirmed**): one appended assistant turn came back as `["assistant", "user"]` with the text after the marker attributed to the user. Whitespace is normalized rather than preserved — `render` trims each turn's tail and `parse` trims both ends, so leading blank lines, leading spaces, `\r\n`, and trailing spaces all come back changed. Normalizing is what makes rendering idempotent, so the loss is acceptable only if the normalized stored form is what verification compares against — which, per the section above, it is not.

### Clauses 3, 7, and 8

Clause 3 has no code. `rendered_previous` re-reads the file and keeps it in a local:

```rust
let previous = rendered_previous(&opened.revision, &path);
```

The sibling owners use `record_write::RecoveryPoint` for exactly this, whose doc comment states the reason this owner needs it: "a crash between the commit and the verifying reread would leave the only copy on a dropped stack, and a failed rollback could not tell the user where their content went". The owner's own `rollback_failed` feedback carries only `expected_revision`, so clause 6's "names the recovery point's location" cannot be satisfied. Adopting `RecoveryPoint` costs nothing here: its `Drop` removes the copy on the success path and on every error path, so the in-memory approach's one advantage is preserved.

Clause 8 is where the contract is inverted rather than partially met. `commit` builds `.{filename}.tmp` and opens it with `File::create`, which truncates through a symlink:

```
produce_ok      = true
victim_exists   = true
victim_content  = "---\nid: \"chat\"\n…\n## user\n\nmy private secret\n"
```

The whole transcript, including the turn content, was written outside the root at an attacker-chosen path, and the owner reported success. `note_resource::commit_atomically` in the same tree defends exactly this and documents why the name must also be unique: "a fixed name plus `create_new` would mean one crash mid-staging leaves a leftover file that blocks every later write to this note forever". That leftover case is live here too — with a directory planted at the staging name, the first append and every subsequent one failed `OwnerUnavailable, retryable: true`, a retryable code for a permanent condition.

Clause 7 is met within one instance. Eight concurrent appends from one shared owner produced one verified success and seven `precondition_failed`, with one turn on disk — no interleaving, no lost turn, and the guard does span recheck → commit → reread → rollback. What is not met is the clause's stated keying: it requires a process-wide registry keyed by file identity, and this is `self.write_lock`. Two instances are constructed today; the second only calls `list`, so the invariant holds by accident of usage rather than by construction. Running two writing instances shows what the keying protects against (**confirmed**, 6 runs): every run ended with one turn on disk, one side failing `OwnerUnavailable` from the staging collision and the other frequently returning `rollback_failed`.

### The pinned ref undoes a correct write

`read` enforces the ref's pinned revision, and `produce` reuses `read` for the post-write reread, so the pin — correct before the write — cannot match after it. On a transcript that already exists (**confirmed**):

```
verified = false   feedback = ("write_rolled_back", retryable: true)
second turn on disk = false
file reverted to its pre-write bytes = true
```

The append was correct, was committed, then was deliberately undone, and the turn is gone. On a first append the same path reports `rollback_failed` instead, because there are no previous bytes to restore, leaving the write in place while telling the caller it could not be verified or restored. `resource.without_revision()` exists and is what the calendar owner uses for this reread.

### Where the write is unbounded and where the read is not

`read` refuses a transcript over 8 MiB; `produce` bounds nothing. One 9 MiB append (**confirmed**):

```
produce         = Ok
file_size       = 9437312
describe after  = Err(PayloadTooLarge, retryable: false)
query after     = Err(PayloadTooLarge, retryable: false)
list after      = 1 row
```

The session remains listed and openable in the UI's session list, and fails permanently the moment it is opened. The content is intact on disk, so the vim test still saves the user, but the product cannot reach a conversation it created. Bounding `content` in the operation schema and checking the projected size before committing keeps the cap meaningful in both directions.

### Coverage

Thirteen owner tests and twelve format tests cover the good paths well: verified append, ordered accumulation, stale revision writing nothing, staging without writing, traversal refusal, denial without the grant, directory-as-list with the temp sibling excluded, recency ordering, metadata refresh, an unknown operation kind refused, and the tolerant-parse cases individually.

Not tested: any assertion that an append preserves what the file already held beyond the turns themselves — `a_hand_edited_transcript_can_still_be_appended_to` asserts the earlier turn's text survives, which is the case that works, and no test uses a hand-edited file with an unknown key, a preamble, or an unclosed fence; a role outside `ROLES` reaching the file (the format test covers `custom`, which is in the table); role/label/resources injection; a revision-pinned ref through any verb; the rollback and `rollback_failed` branches, which no test reaches; staging-name collision, symlink staging, or a blocked staging name; file mode; and the size cap.
