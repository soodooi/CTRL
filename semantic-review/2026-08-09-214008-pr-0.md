# Canonical task Resource owner — one bounded checkbox-line write under the §15.2 contract

`task_resource.rs` makes a note's task list a Resource (`ctrl://local/task/<note>`) with exactly one produce operation, `set_field`, changing one of `status`/`due`/`title`/`tags` on one checkbox line. The owner reads the note's exact bytes as both the revision and the rollback source, refuses values that cannot survive a round trip through the whitespace-delimited checkbox line, delegates the line rewrite to `tasks_source::update` so there is one renderer, and verifies against the stored form rather than the raw request.

Watch for: a revision-pinned ref (`ctrl://local/task/Inbox.md?rev=…`) makes every successful write report `write_unverified` and leaves an orphan cleartext copy of the note behind (**confirmed** by running the owner); a commit failure after the recovery point is captured leaks that copy with nothing naming it and nothing cleaning it up (**confirmed** by running the owner); that same failure is typed `InvalidPayload` when it is an IO fault (**confirmed** by reading and by the run above).

**Verdict**: NEEDS_CHANGES

## High-level view

On the two structural questions the contract turns on: the lock covers the whole critical section — recheck, capture, mutate, reread, and rollback are all inside one guard from `vault_write_lock::for_path(note)`, whose key normalization puts a pinned ref, an unpinned ref, and the legacy `task_update` tool on the same mutex. And there is one writer: `tasks_source::update` commits once through the atomic vault writer, with no path reporting success without reading the value back.

The defect is that `read` does two different jobs. It enforces `resource.revision()` as a precondition, which is right for `describe`/`query`/the pre-mutation recheck and wrong for the post-write reread: after a successful write the revision has by definition moved off the pinned value, so the reread fails and the owner reports a write that landed as `write_unverified` with `observed: null`. The caller is told to retry something already done, and the operation's recovery point is named in the reply and left on disk.

Recovery-point lifecycle has one hole. Every branch that reaches a verdict disposes of the copy correctly — verified discards, restored rollback discards, failed rollback deliberately keeps it and names the location. But `tasks_source::update` returning an error between capture and verdict returns early through `?` with no disposal, and `RecoveryPoint` has no `Drop`, so a verbatim copy of the user's note stays in `~/.ctrl/state/record-recovery` with nothing in the reply referring to it. That same early return mistypes an IO failure (disk full, read-only vault, permission) as `InvalidPayload`, telling the caller their arguments were wrong.

Smaller inconsistency: the `write_unverified` branch reports `expected` as the raw request while the verification comparison and the rollback branch use the normalized stored form, so the two failure replies disagree about what was asked for.

<details>
<summary>Issues (4)</summary>

1. **Pinned-revision ref turns a landed write into `write_unverified`** — the post-write reread goes through `read`, which fails the ref's own `?rev=` precondition once the write has moved the revision. Reread through `resource.without_revision()` (it exists and is currently unused repo-wide) so verification compares against the note, not against the caller's stale pin.
2. **Orphan recovery copy on the pinned-revision path** — that branch names the recovery point in `details` and returns, leaving a cleartext copy of the note outside the vault for a write that succeeded. Fixed by item 1; until then it is a content leak on an ordinary success.
3. **Recovery copy leaked when the commit itself fails** — `tasks_source::update(...)?` returns before any branch disposes of `recovery`, and `RecoveryPoint` has no `Drop`. Either discard it on that path (the note was never touched, so the copy is worthless) or give `RecoveryPoint` a `Drop` that removes the file unless it was deliberately retained.
4. **A write failure is typed as `InvalidPayload`** — `tasks_source::update`'s `TaskError::Vault(Io(...))` is mapped to `InvalidPayload`, so a read-only vault or full disk reads as a bad argument with nothing retryable. Map `TaskError::Vault` to `Unavailable { OwnerUnavailable, retryable: true }` and keep `InvalidPayload` for `NotATask`/`LineOutOfRange`/`UnknownField`/`MissingTitle`.

</details>

### The reread inherits the caller's revision pin

`read` is the owner's only reader and it ends with a precondition:

```rust
if resource.revision().is_some_and(|expected| expected != revision) {
    return Err(ResourceError::Unavailable {
        reason: ResourceUnavailableReason::RevisionUnavailable,
        retryable: false,
    });
}
```

`produce` calls that same `read` for the clause-5 reread, at a point where the revision is *guaranteed* to differ from any pin the ref carried. The ref grammar accepts `?rev=` (`resource.rs` parses it, `mcp_server::produce` forwards the parsed ref untouched, and nothing in the kernel calls `without_revision`), so this is reachable from the gate. ADR-002 §15.2 clause 7's own note — "a revision-pinned and an unpinned ref address the same file" — treats pinned refs as ordinary traffic.

Run against the owner with a pinned ref, a `status: done` write that landed on disk:

```
outcome  = {"feedback":{"code":"write_unverified","details":{"expected":"done","observed":null,
            "recovery_point":".../<key>.bak"}}}
on disk  = "- [x] Pay the invoice 📅 2026-08-10 ✅ 2026-08-09\n"
recovery = [".../<key>.bak"]   // still there
```

`observed: null` is the tell: the reread did not fail to find the task, it failed to open the resource at all. The reply's `retryable: true` invites a retry that will now fail its precondition against the stale pin, so the caller has no route forward except re-reading the note. Every existing test uses an unpinned `reference()`, which is why this is uncovered — `note_resource` has `revision_is_checked_against_the_opened_content` for the pinned read but no pinned produce either.

### The recovery point has no owner between capture and verdict

```rust
let recovery = record_write::RecoveryPoint::capture(...)?;   // file on disk

tasks_source::update(...)
    .map_err(|error| ResourceError::InvalidPayload { message: error.to_string() })?;  // returns
```

`RecoveryPoint` holds only a `PathBuf` and implements no `Drop`, so the copy survives the return and nothing in the error mentions it. Forced by making the vault directory unwritable after the read:

```
result    = Err(InvalidPayload { message: "Io(\"Permission denied (os error 13)\")" })
leftovers = [".../<key>.bak"]
content   = "# Inbox\n\n- [ ] Pay the invoice 📅 2026-08-10\n- [x] Book the room\n"
note      = unchanged
```

The note was never modified, so this copy protects nothing — it is the user's content in cleartext outside the tree they chose for it, the exact condition `discard`'s doc comment and `record_write`'s tests treat as unacceptable. The capture key is derived from scope plus ref, so the file persists until the next write to that note through the same ref shape overwrites it; a pinned and an unpinned ref hash differently and so do not clean up after each other.

The same line mistypes the failure. `TaskError` spans `NotATask`, `LineOutOfRange`, `UnknownField`, `MissingTitle` — all genuine `InvalidPayload` — and `Vault(Io(..))`, which is not: the caller's arguments were fine and the vault could not be written.

### Verification and the two failure replies disagree on `expected`

The verified comparison and the rollback branch both build `expected` from `tasks_source::normalized_field_value`, which is what makes `tags: "work, home"` verify as `work home` and `status: "x"` verify as `done` instead of rolling back a correct write. The `write_unverified` branch instead passes the raw request:

```rust
&record_write::display(&value),
```

So one underlying failure reports `expected: "x"` when the reread fails and `expected: "done"` when the reread succeeds but the value does not match. A surface rendering both through one decision registry shows the user two different asks for one operation.
