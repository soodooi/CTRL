# Governed Markdown note write — third pass on the serialization and staging fixes

The three findings from the second pass are closed. The per-resource lock is now keyed on `resource.id_segments().join("/")` and comes from a new process-wide registry (`kernel/vault_write_lock.rs`), so a pinned and an unpinned ref to the same file take one mutex and `mcp_server::vault_write_lock` delegates to that same registry instead of its own map. The staging sibling carries a nanosecond suffix and every failure inside the staging block unlinks it before returning. Nothing regressed in the earlier seven fixes: `O_NOFOLLOW` plus `create_new`, the `~/.ctrl/state/note-recovery` recovery point with file and directory fsync, the lock spanning recheck → recovery → commit → reread → rollback, scope and stale-revision rejection in every verb, and owner-only review facts all hold, and §15.2 clauses 7 and 8 spell out the vault-relative lock keying and the unlink rule in the ADR body. `cargo test --lib` is 581 passed / 0 failed, with 18 note_resource tests including a leftover-staging test and 3 new lock-registry tests.

Watch for: the error path unlinks the staging path even when the failure was `create_new` refusing an existing entry (confirmed), so a second OS process — or an attacker-planted artifact at that exact dotted name — has its file removed by a writer that never created it; and two carry-overs from the prior pass are still open by design or omission, namely the single overwritten `sha256(ref).bak` recovery file (confirmed) and the unenforced "recovery root outside the content tree" rule (confirmed).

**Verdict**: APPROVED — the three scoped findings are closed and no drift appeared. The unlink-precision item and the two carry-overs are non-blocking; none of them can produce a partial write, a lost verified commit, or an escape from the authorized root.

## High-level view

Lock identity is now correct and shared. `vault_write_lock::for_path` normalizes away empty and `.` segments, so `daily/today.md`, `./daily/today.md`, and `daily//today.md` resolve to one `Arc<Mutex>`; the note owner keys on `id_segments`, which excludes `revision`, and `mcp_server` keys on the vault-relative `args.path` it already had. Canonical `produce` and every legacy vault verb therefore contend on one authority per file, which is what closes the rollback-reverts-a-legacy-write hole.

The staging trap is gone: the temporary name includes a nanosecond component and the write/flush/rename sequence is wrapped so any error unlinks the temp file. The unlink is one step too broad — it also runs when `create_new` failed, meaning the file being removed belongs to someone else. Nothing is corrupted (the failing writer already returned `Unavailable { retryable: true }` and the target is untouched), but the other writer's subsequent `rename` then fails on a missing source, so a cross-process collision degrades both writers instead of only the loser. Removing the temp only after a successful create keeps the availability fix without touching files this call did not create.

`mcp_server` keeps a now-unused `vault_write_locks` field, held alive by a `let _ = &self.vault_write_locks;` statement so the compiler stays quiet. It is a second registry that no longer governs anything; leaving it in place invites a future writer to lock the wrong map.

The two residuals from the prior pass are unchanged. The recovery point is still one `sha256(ref).bak` per resource, so a later write overwrites the earlier safety copy and nothing prunes the directory — acceptable while rollback consumes the file inside the same critical section, but the "hand-recoverable" promise in clause 6 covers only the most recent operation. And clause 3's containment is still a doc comment: `with_recovery_root` accepts any path, and a vault root configured beneath `~/.ctrl` would place recovery files inside user content with no failure. The production-constructor test asserts the default pair is disjoint, which is narrower than the clause.

<summary>Issues (3)</summary>

1. **Unlink runs on a create it did not perform** (confirmed) — `commit_atomically` removes the staging path whenever the closure errs, including an `EEXIST`/`ELOOP` failure from `create_new`, deleting another process's staging file or a planted artifact. Unlink only after the create succeeds.
2. **Dead second lock registry in `mcp_server`** (confirmed) — `vault_write_locks` is kept alive only by `let _ = &self.vault_write_locks;` in `vault_write_lock`; remove the field so one registry is the only reachable authority.
3. **Recovery-point retention and root containment still unenforced** (confirmed, carried over) — one overwritten `sha256(ref).bak` per resource with no pruning, and clause 3's "outside the content tree" is a comment that neither `with_recovery_root` nor a vault root under `~/.ctrl` is checked against.

### The three findings, verified closed

Lock keying: `MarkdownNoteOwner::write_lock` calls `super::vault_write_lock::for_path(&resource.id_segments().join("/"))`. `ResourceRef::id_segments` returns only the path segments — `revision` is a separate field and appears solely in `Display` — so a `?rev=`-pinned ref and a bare ref hash to the same key. `equivalent_paths_share_one_lock` and `different_files_do_not_share_a_lock` pin the normalization; `the_guard_serializes_writers_on_one_path` proves the second acquirer waits.

Staging name and cleanup:

```rust
let temporary = directory.join(format!(".{}.{unique}.ctrl-tmp", file_name));
let staged = (|| -> Result<(), ResourceError> {
    let mut file = OpenOptions::new().write(true).create_new(true)
        .custom_flags(libc::O_NOFOLLOW).open(&temporary)?;
    file.write_all(...)?; file.sync_all()?;
    std::fs::rename(&temporary, path)
})();
if staged.is_err() { let _ = std::fs::remove_file(&temporary); return staged; }
```

`write_all` and `sync_all` failures now unlink; the open-failure case shares that unlink, which is issue 1. `staging_leaves_no_leftover_file_that_could_block_later_writes` covers the intended path and `a_planted_link_at_a_predictable_name_cannot_capture_the_write` still passes with the unique name.

Shared registry: `mcp_server::vault_write_lock` is `crate::kernel::vault_write_lock::for_path(path)`; all 20-odd legacy call sites (`vault_write`, doc block ops, task multi-note guards, image write, smart-table produce) go through it, so canonical and legacy writes on one path serialize.

### Drift checks

Serialization span: `produce` takes the guard before `self.read(resource)` and holds it through the recheck, `write_recovery_point`, `commit_atomically`, the post-write reread, and both rollback branches. Success is only reported when the reread revision equals `sha256(content)`, with `effect.verified_by` naming the check; failure to restore is non-retryable and carries the recovery path.

Scope and revision: `authorize_context` requires `*`, `notes`, or `vault` and runs first in `describe`, `query`, `stage`, and `produce`; both `stage` and `produce` compare `expected_revision` against a freshly read revision, and `produce` re-reads under the lock.

Review facts: `PreparedProduce::review_facts` calls the owner's `stage` and projects `Outcome::review_facts()`, which returns `None` when nothing is staged. `ReviewRequest.outcome` has no other producer; `mcp_server` passes it through `request_with_outcome` only on the non-user-surface branch.

ADR: §15.2 clause 7 states the critical section spans recheck through rollback, clause 8 requires a unique name plus exclusive no-follow semantics and that "every staging failure unlinks the temporary file," and the paragraph after clause 8 states the registry is process-wide and keyed by vault-relative file identity rather than ResourceRef text, naming both the pinned/unpinned case and the legacy-write case. INDEX carries v87 for ADR-002; `pipeline-conformance.json` keeps U6/U10/U11 at `partial`.

`node scripts/check-governance.mjs` still reports blocked citations in `IrisyChat.tsx`, `kernel.ts`, and `commands/skills.rs`. None of those files is in this slice.
