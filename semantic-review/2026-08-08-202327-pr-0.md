# Governed Markdown note write — second pass after the seven fixes

All seven previously raised findings are closed in code and in the ADR. The recovery point now defaults to `~/.ctrl/state/note-recovery` in both production constructors, is written with `sync_all` on the file plus a best-effort directory fsync, and uses a `.bak` name; the staging sibling is opened with `create_new(true)` plus `O_NOFOLLOW` and the parent directory is fsynced after `rename`; `produce` holds a per-resource async mutex across recheck → recovery → commit → reread → rollback; `stage`'s `precondition_failed` now carries the addressed ref; the `produce` tool description no longer claims universal ReviewGate coverage; ADR §17.4 records that owner-side capability scope is caller-declared and must not be read as proof of user intent; and the v87 changelog states the U6/U10/U11 move from `declared` to `partial`. Clauses 7 and 8 exist in the §15.2 body, not only the changelog. `cargo test --lib note_resource` is 16/16, including new tests for the recovery root location, the planted staging link, concurrent writers, and the stale-stage ref.

Watch for: the per-resource lock is keyed on `resource.to_string()`, which includes `?rev=`, so two concurrent writers spelling the same file differently take different locks and clause 7 does not hold (confirmed); a staging sibling left behind by a failed `write_all`/`sync_all` permanently blocks every later write to that note, because the name is fixed and `create_new` then always fails (confirmed); and the canonical path's lock is disjoint from `vault_write_locks`, so a legacy vault verb writing the same file can still be reverted by a canonical rollback (confirmed).

**Verdict**: NEEDS_CHANGES — three concrete must-fix items, all in the new serialization/staging code; the seven prior findings are closed.

## High-level view

The write contract now matches the eight ADR clauses clause-for-clause, and the previously-flagged containment and durability holes are gone. Reads and the pre-mutation recheck go through `StableRoot`/`open_beneath`; the commit creates `.{name}.ctrl-tmp` with `O_EXCL | O_NOFOLLOW`, flushes, renames (which never follows a link at the final component), and fsyncs the parent. The planted-link test proves the write aborts and nothing lands outside the root.

Serialization is present but its key is wrong. `write_lock` uses the full ref string, and `ResourceRef`'s `Display` includes `?rev=<revision>`. Two `produce` calls on the same note — one pinned, one not, or pinned at different revisions that both resolve — acquire different mutexes and reproduce exactly the interleaving clause 7 was added to prevent: both pass the recheck, the second reread mismatches, and the loser's rollback restores its recovery point over content the winner already reported as `effect.verified_by`. The lock must key on the file identity (`id_segments`), not the ref spelling.

The `O_EXCL` fix trades a symlink hole for an availability trap. The temp name is fixed per note, and the failure paths inside the staging block (`write_all`, `sync_all`) return without unlinking the temp file; only `rename` failure cleans up. After one disk-full or crash mid-staging, every subsequent write to that note fails `Unavailable { retryable: true }` forever with no self-healing and no operator-visible reason. A unique per-operation suffix plus cleanup on every error exit keeps the no-follow guarantee without the trap.

Cross-surface serialization is still absent: legacy vault verbs in `mcp_server.rs` take `vault_write_lock(path)`, the note owner takes its own map. A legacy write landing between the canonical recheck and reread is seen as a verification mismatch and rolled back.

Two smaller residuals carry over. The recovery filename is still a fixed `sha256(ref).bak`, so each write overwrites the previous safety copy and nothing prunes the directory; and `recovery_root` "must never point inside the vault" is a comment, not a check — a configured vault root under `~/.ctrl` would violate clause 3 with no failure. Review facts remain owner-derived only (`ReviewRequest.outcome` is exclusively `Outcome::review_facts()` from the owner's `stage`, `None` when nothing staged), scope is enforced in every verb, and stale revisions are rejected on both stage and produce paths.

<details>
<summary>Issues (5)</summary>

1. **Lock key includes the revision** (confirmed) — `write_lock` keys on `resource.to_string()` and `Display` emits `?rev=`, so writers addressing one file with different ref spellings never serialize; clause 7 is bypassed. Key on `id_segments()` (or the resolved file identity) instead.
2. **Stale staging sibling blocks all later writes** (confirmed) — the fixed `.{name}.ctrl-tmp` plus `create_new` means one leftover temp file makes every future write to that note fail; `write_all`/`sync_all` failures do not unlink it. Use a unique per-operation suffix and remove the temp on every error path.
3. **Canonical and legacy writes are not mutually serialized** (confirmed) — the owner's map is disjoint from `vault_write_locks`, so a legacy vault write on the same file can be reverted by the canonical rollback. Share one lock authority per path across both surfaces.
4. **Recovery point still overwritten, no retention** (confirmed) — one `sha256(ref).bak` per resource; the next write destroys the previous copy and nothing cleans the directory. Make each recovery point distinct per operation and define retention.
5. **Recovery-root containment is unenforced** (confirmed) — clause 3's "outside the user's content tree" is a doc comment; `with_recovery_root` and a vault root configured under `~/.ctrl` can both violate it silently. Reject a recovery root that resolves inside the vault root.

### Prior findings, verified closed

Recovery point (1): `default_recovery_root()` → `$HOME/.ctrl/state/note-recovery`, used by both `new()` and `from_default_vault()`; the default vault root is `~/Documents/CTRL`, so the two are disjoint. `write_recovery_point` writes `<sha256(ref)>.bak`, calls `sync_all` on the file, then fsyncs the directory; every failure maps to `Unavailable` and aborts before the note is touched (`an_unwritable_recovery_point_aborts_before_mutating`). `the_recovery_root_is_never_inside_the_content_tree` asserts on the production constructor, not the test helper.

Staging sibling (2): `OpenOptions::new().write(true).create_new(true).custom_flags(libc::O_NOFOLLOW)`, then `write_all`, `sync_all`, `rename`, then `File::open(directory).sync_all()`. `a_planted_symlink_cannot_redirect_the_staged_write` proves the write aborts, the outside target is not created, and the note keeps its original bytes.

Serialization (3): `produce` acquires `write_lock(resource)` before the recheck and holds it through the rollback branch; `concurrent_writers_do_not_interleave_recheck_and_commit` asserts exactly one verified success and one `precondition_failed`, with the winner's bytes surviving. The mechanism is right; the key is not (issue 1).

Stale stage ref (4): `precondition_failed(resource, ...)` clones the addressed ref, asserted by `a_stale_stage_names_the_real_resource_in_its_failure`.

Tool description (5): now "A call from an autonomous caller passes through ReviewGate; direct user-surface actions are governed by the existing gate policy instead," which matches the `is_user_surface` / `ReviewGate::enforcing()` branch.

ADR (6, 7): §17.4 states declared scope must not be treated as proof of user intent and that a non-loopback or multi-principal caller needs an accepted scope-to-principal binding before it may write. The v87 changelog ends with "This moves ADR-005 §12 U6/U10/U11 from `declared` to `partial`; no frontend caller exists yet, so none of them is `verified`," and `pipeline-conformance.json` agrees: all three are `partial` with `failingStages: ["declaredGaps"]` and name the missing frontend caller, the approval adapter that does not yet read `request.outcome`, and the legacy string-flattened tools.

### Drift checks

No write without capability scope: `authorize_context` runs first in `describe`/`query`/`stage`/`produce`; a `registry`-scoped caller is denied with the file untouched. Scope itself still arrives from the caller's `X-Ctrl-Intent` via `canonical_resource_context`, which §17.4 now records.

No write on a stale revision: both `stage` and `produce` compare `expected_revision` against a freshly read revision, and `produce` re-reads under the lock.

Review facts cannot be fabricated: `PreparedProduce::review_facts` calls the owner's `stage` and projects `Outcome::review_facts()`; there is no other constructor for `ReviewRequest.outcome`, and a non-staged operation yields `None` rather than an argument dump.

### Out of scope

`node scripts/check-governance.mjs` reports blocked citations in `IrisyChat.tsx`, `kernel.ts`, and `commands/skills.rs`. None of those files is in this slice.
