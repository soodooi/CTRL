# Canonical calendar event Resource owner — one bounded frontmatter field write under the §15.2 contract

`calendar_resource.rs` makes one event note a Resource (`ctrl://local/calendar/<event note>`) with a single produce operation, `set_field`, changing one of `title`/`date`/`start`/`end`/`location`/`tags`. The owner hashes the note's whole bytes as the revision, holds one per-note lock across recheck → capture → write → reread → rollback, captures the previous bytes outside the vault before touching anything, verifies against `calendar_source::normalized_field_value` rather than the raw request, rereads through `resource.without_revision()`, and restores byte-exactly through `vault::restore_raw`. The three defect classes found in the sibling owners are all absent here.

Watch for: the delegated writer reformats the whole frontmatter block on every one-field change, so an untouched `start: "09:00"` comes back as unquoted `start: 09:00` — which a YAML 1.1 parser reads as the integer 540, and `10:00` as 600 (**confirmed** by running the owner and by parsing the output with `yaml@2.9.0` at `version: '1.1'`); a CRLF note's frontmatter is flattened to LF while its body keeps CRLF, producing a mixed-ending file reported as a verified success (**confirmed** by running the owner); the test named `a_rollback_restores_the_event_note_byte_for_byte` neither rolls back nor asserts byte-exactness, and its comment-preservation claim is false (**confirmed** — the comment is destroyed on the ordinary success path).

**Verdict**: NEEDS_CHANGES

## High-level view

The contract's structural clauses hold. One guard from `vault_write_lock::for_path(note)` spans the entire critical section, and because that registry is process-wide and keyed by normalized vault-relative path, the canonical owner and the surviving legacy `calendar_produce` tool serialize against each other on the same note rather than holding separate locks. The commit reaches disk through `vault::write_atomically` (unique dot-prefixed sibling, `O_EXCL | O_NOFOLLOW`, mode preserved, flushed, renamed, parent synced). Rollback goes through `vault::restore_raw`, which writes the captured bytes verbatim and then calls `refresh_index_for`, so a rolled-back note is not left findable by the text of a reverted change.

The three defect classes from the sibling reviews are fixed here, each with a test that would catch a regression. Verification compares against `normalized_field_value`, so a comma-separated tag list and a whitespace-bearing `"  Room 3  "` both verify instead of rolling back a correct write; across 27 probe values — YAML-significant tokens, embedded newlines, tabs, a NUL, U+2028, a 400-character string — I found no divergence between the normalized form and the stored form. The reread goes through `without_revision()`, so a revision-pinned ref still reports a verified success. And `RecoveryPoint` has a `Drop`, so forcing a commit failure by making the calendar directory read-only mid-operation left the recovery directory empty.

What remains is the fidelity class, the one the v90 changelog claims was fixed. That fix landed in the task writer, which moved to `vault::write_body` so that "a one-field task edit" stopped being "a whole-file reformat". `calendar_source::set_event_field` still commits through `vault::write`, which re-emits the frontmatter block from parsed JSON: on a single `location` change it destroys comments on untouched keys, unquotes quoted times, expands a flow list to a block list, flattens CRLF frontmatter to LF, and inserts a blank line after the closing fence — all reported as a verified success, because the reread only inspects the one field that changed (**confirmed**). The surgical patcher this needs already exists in the same module, `vault::patch_frontmatter_key`, and preserves every one of those on the same inputs, but two caveats block a straight swap.

Two smaller gaps. A vault IO fault surfaces as `InvalidPayload`, telling a caller their argument was wrong when the disk was full or the vault read-only; the code comments this honestly and attributes it to `ProduceError` collapsing IO into `Conflict`, but the owner can still distinguish it (**confirmed**). And clause 6's rollback branch is unreachable by any input I could construct, so the one clause that protects the user's content on a mismatch is exercised by no test through this owner (**confirmed** for the 27 values probed; **possible** that some value diverges — it would need a form where the YAML round trip is not identity).

<summary>Issues (6)</summary>

1. **A one-field change reformats the whole frontmatter block** — `set_event_field` commits through `vault::write`, which re-renders the block from parsed JSON: comments on untouched keys are destroyed, quoted scalars lose their quotes, flow lists become block lists, and a blank line is inserted after the closing fence. Route it through `vault::patch_frontmatter_key`, as the task writer was moved to `write_body` for this reason in the same commit. Two caveats to close first: that patcher commits with a plain `fs::write` rather than `write_atomically`, which would regress clause 4, and it renders values only as strings, so `tags` would land as a scalar instead of the YAML array `tags_of` reads back.
2. **Unquoted times are a YAML 1.1 interop hazard** — re-rendering turns `start: "09:00"` into `start: 09:00`. serde_yaml reads it back as a string so CTRL round-trips fine, but a YAML 1.1 parser reads `09:00` as 540 and `10:00` as 600, and the module's stated compatibility target is an existing Obsidian Full Calendar vault. Fixed by item 1 for untouched keys; `create_event` needs the same treatment for the keys it writes.
3. **CRLF frontmatter is flattened while the body keeps CRLF** — a CRLF event note comes back with an LF frontmatter block and a CRLF body, a mixed-ending file, reported as a verified success. `patch_frontmatter_key` already detects and preserves the block's line ending.
4. **A plain note in `calendar/` gains a frontmatter block** — a note with no frontmatter scans as a row with empty fields, so `set_field` succeeds on it and writes a frontmatter block plus a blank line into what was plain text. Either refuse a note that carries no event frontmatter, or preserve the plain shape.
5. **The byte-for-byte test does not test byte-for-byte, and clause 6 is uncovered** — `a_rollback_restores_the_event_note_byte_for_byte` triggers no rollback and asserts `before.contains("# keep me")` on the pre-image; the comment is in fact destroyed by the write. Rename it to what it covers (a trimmed value verifies) and add a rollback test that drives a real mismatch, e.g. by injecting a writer that stores a different value.
6. **An IO fault is typed `InvalidPayload`** — a read-only vault surfaces as `InvalidPayload { message: "conflict: Io(\"Permission denied\")" }`, so a caller reads a disk fault as a bad argument with nothing retryable. `ProduceError` collapses both into `Conflict`, but the owner can separate them by giving `ProduceError` an IO variant, or map to `Unavailable { OwnerUnavailable, retryable: true }` when the message is an IO error.

### The delegated writer re-renders what it was asked to leave alone

Delegating so there is one writer is the right call; the writer it delegates to rebuilds the block.

```rust
let entry = vault::read(root, path).map_err(map_vault_err)?;
let mut fm = object_or_empty(entry.frontmatter);
// ... obj.insert(field, ...)
vault::write(root, path, &entry.content, &fm).map_err(map_vault_err)?;
```

`vault::write` emits `format!("---\n{yaml}---\n\n{content}")` from `frontmatter_to_yaml`, so everything not representable in parsed JSON is gone. Running a `location` change against a note that exercises each shape (**confirmed**):

```
BEFORE                          AFTER
title: Standup  # keep me       title: Standup
date: 2026-08-05                date: 2026-08-05
start: "09:00"                  start: 09:00
end: "09:15"                    end: 09:15
tags: [work, planning]          tags:
nested:                         - work
  a: 1                          - planning
---                             nested:
Body, no blank line.              a: 1
                                location: Room 3
                                ---
                                                    <- blank line inserted
                                Body, no blank line.
```

`is_verified_success()` returns true for that write. Clause 5's reread compares one field, so a whole-file reformat passes it — the same blind spot the v90 changelog describes for the task writer ("both reported as verified successes because the reread only inspected the changed field").

Key order of the surviving keys does survive, so the damage is bounded to comments, quoting, collection style, line endings, and the body separator.

`vault::patch_frontmatter_key` splices only the matched key's line span and reassembles the rest byte-identically, and fails closed on the one YAML-legal shape its span rule cannot edit safely. On the same inputs (**confirmed**):

```
---PATCHED---
title: Standup  # keep me
start: "09:00"
tags: [work, planning]
location: Room 3
---
Body, no blank line.

CRLF: "---\r\ntitle: Standup\r\nstart: \"09:00\"\r\nlocation: Room 3\r\n---\r\nBody.\r\n"
```

Comment, quotes, flow list, absent blank line, and CRLF all preserved. Two things block a straight swap, both worth fixing rather than working around: it commits with `fs::write`, not `write_atomically`, so adopting it as-is trades clause 4 for fidelity; and `render_fm_entry` always renders a string, so `tags` would become `tags: work, planning` instead of the array `tags_of` expects.

### The time-quoting change is the one that can be read wrong elsewhere

Most of the reformatting is churn against the plain-text-first commitment. The time fields are different, because the value's *meaning* depends on the reader's YAML version (**confirmed**):

```
yaml@2.9.0  version:'1.1'   start: 10:00    -> 600
yaml@2.9.0  version:'1.1'   start: 09:00    -> 540
yaml@2.9.0  version:'1.1'   start: "10:00"  -> "10:00"
yaml@2.9.0  version:'1.2'   start: 10:00    -> "10:00"
js-yaml@4.1.1 (1.2 default) start: 10:00    -> "10:00"
```

Inside CTRL this is invisible: serde_yaml follows the 1.2 core schema, so the unquoted form reads back as the string, a second write verifies, and `query` reports `start: "10:00"` throughout — checked across both the first and second write. The exposure is external, and this module's stated substrate is "the Obsidian Full Calendar note-per-event convention, so … an existing Obsidian calendar vault reads as-is". A tool on the YAML 1.1 side of that boundary sees a sexagesimal integer where the user wrote a time. This also applies to `create_event`, which writes `start`/`end` through the same renderer, so newly created events carry the unquoted form from birth — outside this diff's changed lines, same root cause and same fix.

### Clause 6 has no reachable input, so the protection is untested here

The rollback branch requires `observed != expected`, where both sides derive from the same two functions:

```rust
let expected = record_write::display(&normalized_field_value(&field, &value)...);
let observed = Self::field_value(&committed.row, &field);   // display(row.get(field))
```

`normalized_field_value` composes exactly the store-and-project pair (`tags_value` + `tags_of` for tags, `trim` for the rest), which is what makes the verification-operand fix work. I tried to break the equality with 27 values — `true`, `null`, `~`, `no`, `yes`, `0900`, `1.50`, `2026-08-05`, `a\nb`, `  spaced  `, `#hash`, `Room\r3`, `\t tabbed \t`, `a: b`, `- item`, `*anchor`, `&anchor`, `!!str x`, `{a: 1}`, `[1,2]`, `trailing\`, U+2028, NUL, a 400-char string, `e`, and empty — and every one verified. The consequence is that the branch which restores the user's content is exercised by nothing. `restore_raw` itself does put the exact bytes back (driven directly against a mutated note, the file matched the original), but the owner's path into it is unproven.

The test that appears to cover this does not. `a_rollback_restores_the_event_note_byte_for_byte` performs a *successful* write, and its only comment-related assertion reads the pre-image:

```rust
assert!(before.contains("# keep me"));
```

`before` was captured before the write, so it holds regardless of behavior. The comment is in fact destroyed — the same run shows `after` without it. The test's real content is the trimmed-value assertion; its name and its clause-6 citation claim coverage that does not exist.
