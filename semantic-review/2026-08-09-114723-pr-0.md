# Task Resource write path — re-review of five prior findings

Scope is the three files named for re-review: `record_write.rs`, `task_resource.rs`, `tasks_source.rs`. All five previously-raised issues are closed, each with a mechanism I could read and, where relevant, a test that fails without it: a durable pre-write recovery point under `~/.ctrl/state/record-recovery`, rollback through `vault::restore_raw` (raw bytes, atomic), verification against `tasks_source::normalized_field_value` derived from the same code that stores the value, `vault::write_body` plus a CRLF-aware `rejoin` so a one-field edit is a one-line edit, and the accepted value shapes stated in the `set_field` input schema. The new failure mode is in the recovery point itself: its filename is `sha256(ResourceRef)` only, which ignores the vault root, so two owners on the same relative note path share one recovery file — reproducible today as a test failure.

Watch for: recovery-point key collides across vault roots and makes the narrow test command fail deterministically (confirmed — 3/3 runs of `cargo test --lib -- task_resource:: record_write::`); `read_raw(...).unwrap_or_default()` turns an unreadable note into an empty-string recovery point that a rollback will then write over the file (confirmed in code, race-triggered); recovery files are never removed after a verified write, so note content accumulates in cleartext outside the vault (confirmed); a CRLF note *with* frontmatter still has its fence/body separator emitted as LF (likely, untested).

**Verdict**: NEEDS_CHANGES

## High-level view

Clause 3 now has a real recovery point. `RecoveryPoint::capture` writes the previous bytes to `$HOME/.ctrl/state/record-recovery/<key>.bak`, `sync_all`s them, and aborts the operation when it cannot — and `produce` calls it before touching the note. `rollback_failed` and the unverifiable-reread path both carry `recovery_point` in `details`, so the non-retryable case names a location. The remaining problem is the key: `sha256(resource.to_string())` carries no vault root, and `TaskResourceOwner` is constructed per root, so two roots addressing `Inbox.md` write the same `.bak`.

Rollback is now faithful. `opened.raw` comes from `vault::read_raw` and goes back through `vault::restore_raw`, which writes those bytes atomically and touches nothing else; the frontmatter round-trip test asserts byte equality including a comment and a hand-chosen key order. The one soft spot is the fallback: `read_raw` failure degrades to `String::new()`, and `produce` then uses that value both as the recovery point and as the rollback source.

Verification compares like with like. `tasks_source::normalized_field_value` is the storing code's own view of the value — `normalize_status_word` for status, `parse_tag_list(..).join(" ")` for tags — so `#work, home` and `DONE` verify instead of rolling back, each with a test.

The write is bounded to the addressed line. `update` and `delete` now go through `vault::write_body`, which keeps the raw frontmatter prefix, and `rejoin` picks the terminator the note actually uses instead of collapsing CRLF to LF. Two gaps remain: a note with *mixed* endings is normalized to CRLF wholesale, and for a CRLF note that has frontmatter `write_body` joins prefix and body with `\n\n`.

The schema states the shapes. The `value` property's description names the status synonyms, the `YYYY-MM-DD`-or-empty due format, and comma-separated tags with an optional `#`. It is prose inside one shared `value` string rather than per-field constraints, which is the honest limit of a single-field union.

<summary>Issues (6)</summary>

1. **Recovery key ignores the vault root** — `RecoveryPoint::capture` keys the file by `sha256(ResourceRef)` alone, so every root sharing a relative note path shares one `.bak`; `cargo test --lib -- task_resource:: record_write::` fails 3/3 because two test modules collide on `ctrl://local/task/Inbox.md`. Include the owner's root (or an operation-unique suffix) in the key.
2. **Empty-string recovery point on an unreadable note** — `read` does `read_raw(..).unwrap_or_default()` and `produce` uses that unconditionally, so a note that vanishes between the two reads yields a `""` recovery point and a rollback that truncates the file. Make `raw` an `Option` and refuse to write (or refuse to roll back) when it is absent.
3. **Recovery files are never reclaimed** — nothing removes the `.bak` after a verified write, so previous note contents persist in cleartext under `~/.ctrl/state` indefinitely, including from test runs. Delete on verified success and bound the directory.
4. **Tests write to the real HOME** — `record_write` and `task_resource` tests exercise `capture` against the developer's actual `~/.ctrl/state`, leaving files behind and coupling unrelated tests. Make the recovery root injectable for tests.
5. **CRLF note with frontmatter still gets an LF separator** — `write_body` emits `{prefix}\n\n{body}`, so the fence/body boundary of an otherwise-CRLF note changes; the CRLF test covers only the frontmatterless case. Add the frontmatter+CRLF case and emit the note's own terminator.
6. **Mixed line endings are normalized wholesale** — `rejoin` chooses CRLF if the body contains a single CRLF, rewriting every LF line in a mixed-ending note. Preserve per-line terminators or leave untouched lines alone.

### Clause 3: recovery point exists, but its name is not unique enough — STILL OPEN (as a new defect)

`capture` is called in `produce` after the precondition recheck and before `tasks_source::update`, propagates as an error rather than proceeding without a recovery point, and `sync_all`s before returning. The `.bak` extension is deliberate so the file can never read as a note.

The key is the problem:

```rust
let key = format!("{:x}", Sha256::digest(resource.to_string().as_bytes()));
let path = root.join(format!("{key}.bak"));
```

`ResourceRef` names the note relative to a vault; the root lives on the owner (`TaskResourceOwner::new(root)`), not in the ref. `File::create` truncates. So the last writer to any `Inbox.md` — a second vault, a test root, a future second owner instance — replaces the only copy of someone else's previous content. This is not theoretical:

```
$ cargo test --lib -- task_resource:: record_write::
---- kernel::record_write::tests::a_rollback_distinguishes_restored_from_not_restored stdout ----
assertion `left == right` failed
  left: "# Inbox\n\n- [ ] Pay the invoice 📅 2026-08-10\n- [x] Book the room\n"
 right: "previous bytes\n"
test result: FAILED. 37 passed; 1 failed
```

Three consecutive runs of that command fail; the full `cargo test --lib` run passes 688/688 three times, so this is timing-dependent rather than absent. The narrow command is the one the kernel rules prescribe, which makes it the command most likely to be run.

The same run shows the retention half. After the suite, real user HOME holds:

```
~/.ctrl/state/record-recovery/1e5b6142….bak   283 bytes
~/.ctrl/state/record-recovery/d7194c82….bak   121 bytes
```

Nothing deletes these on a verified write, so the directory grows one file per written resource and holds note text in cleartext outside the vault — content the user would expect to live only in their content tree.

### The rollback source can be an empty string

```rust
let raw = super::vault::read_raw(self.root()?, &note).unwrap_or_default();
```

The comment says unreadable raw bytes "only mean this read cannot be the basis of a rollback," but nothing enforces that: `produce` feeds `opened.raw` to `capture` and to `restore_raw` without checking whether it was ever read. `vault::read` and `read_raw` both go through `fs::read_to_string`, so this needs the file to change between the two calls — the per-note lock is process-internal and does not cover an external editor or `rm`. In that window a failed verification writes a zero-byte note and records a zero-byte recovery point, which is worse than either reporting `write_unverified` or refusing the write.

### Revision covers the body, not the note

`read` documents that "the revision covers the whole note, because any edit to it can move the line a task lives on," but hashes `entry.content`, which `vault::read` returns with the frontmatter split off. A frontmatter-only edit between the caller's read and its write therefore passes the precondition, and `precondition_failed`'s message ("the note changed since it was read") is broader than what is actually checked. Line addressing is body-relative so the write still lands on the intended task, and the rollback bytes are captured fresh inside the lock — the consequence is a claim in the comment and in user-facing copy that the code does not make.

### Verification against stored value — CLOSED

`normalized_field_value` lives next to `update` and reuses `normalize_status_word` and `parse_tag_list`, so the two operands cannot drift by construction, and `field_value` renders the parsed item through the same `record_write::display` used for staging. `a_multi_tag_write_verifies_instead_of_rolling_back` and `a_status_synonym_verifies_instead_of_rolling_back` (over `x`, `complete`, `completed`, `DONE`) both pass and both fail against the old raw-request comparison. `normalized_field_value` returning `None` falls back to the raw value, so a field added later without a normalization arm would verify against the request again rather than silently against nothing.

### Bounded write — CLOSED, with a residual on CRLF plus frontmatter

`update` and `delete` no longer route through `vault::write`; they call `vault::write_body`, which preserves the raw frontmatter prefix verbatim and leaves a frontmatterless note frontmatterless, and `rejoin` restores the terminator `str::lines` discards. `a_plain_note_does_not_gain_a_frontmatter_block`, `a_field_change_leaves_the_frontmatter_bytes_untouched`, and `a_crlf_note_keeps_its_line_endings` all pass.

Two cases are outside what those tests cover. `write_body` composes `format!("{prefix}\n\n{body}")`, so a CRLF note carrying frontmatter gets an LF fence/body separator — smaller than the previous whole-file reflow, and not a regression, but still a byte the caller did not ask to change. And `rejoin`'s terminator choice is all-or-nothing:

```rust
let terminator = if original.contains("\r\n") { "\r\n" } else { "\n" };
```

One CRLF anywhere in a mixed-ending note converts every other line to CRLF.

### Schema states the shapes — CLOSED

The `set_field` input schema's `value` property carries: "status: todo | doing | done (also x, complete, completed, any case). due: YYYY-MM-DD or empty to clear. title: text. tags: comma-separated, a leading # is optional." That is the writer's actual contract — `normalize_status_word`'s synonym set and `parse_tag_list`'s comma split with optional `#` — so a caller no longer has to learn the tags shape from a rollback.

### Smaller observation

`read` maps every `vault::read` failure to `Unavailable { retryable: true }`, so a task ref naming a note that does not exist reports as a transient outage the caller should retry rather than as a missing note.
