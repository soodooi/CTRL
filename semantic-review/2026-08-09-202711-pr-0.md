# Recovery points and in-place line edits for task writes

`record_write.rs` is new: shared Outcome shapes for record-source writes (stale precondition, unverified write, rollback) plus `RecoveryPoint`, which copies a note's previous bytes under the kernel state root before anything is mutated. `tasks_source.rs` swaps its split-and-rejoin body rewrite for `splice_line` / `remove_line`, which edit one line and copy every other byte through, and writes via `vault::write_body` so the frontmatter block keeps its exact bytes. It also gains `normalized_field_value`, the operand the Resource owner compares a post-write reread against. All four prior findings are closed. Two new defects: `normalized_field_value` does not report what the source actually stores for any value carrying whitespace, so a legitimate write fails verification and is rolled back; and the recovery file survives on disk, unreported, on the successful-rollback path.

**Watch for:** `normalized_field_value` is not the round-trip of the store for whitespace-bearing `due` or `tags` values, contradicting its own docstring (confirmed, reproduced); a restored rollback leaves an orphan recovery file holding user content in cleartext, with its path in no reply (confirmed); recovery files are created world-readable (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The four prior findings are closed, verified by running the code rather than reading it. `RecoveryPoint::capture` takes the content root as `scope` and hashes `scope + resource`, so two vault roots holding the same relative path get separate `.bak` files; `cargo test --lib -- task_resource:: record_write:: tasks_source::` is 42 passed / 0 failed. `discard()` exists and the task owner calls it on the verified-success path. Every `capture` call site in tests passes an explicit temp root. `rejoin` is gone: a note mixing CRLF and LF keeps each line's own terminator.

`splice_line`, `remove_line`, and `terminator_of` are correct on every edge case asked about — no final newline, index past the end, empty body, lone `\r`. The one that matters structurally is the lone `\r`: `str::lines` and `split_inclusive('\n')` both decline to split on it, which is what keeps the `lines()`-based target lookup and the `split_inclusive`-based splice addressing the same line.

The real defect is the verification operand, not the line editing. `normalized_field_value` reimplements the normalizer instead of round-tripping through render-then-parse, so it diverges from the store whenever a value carries whitespace, and the owner rolls back a write the source performed correctly. The note is corrupted between the write and the restore, so a failed `restore_raw` leaves a mangled title behind.

The recovery-point lifecycle has one hole: `write_rolled_back` attaches `recovery_point` only when `restored` is false, and no caller discards the file when the restore succeeds, leaving a cleartext copy of the user's note under `~/.ctrl/state` that nothing reports and nothing cleans up. Separately, `capture` uses `File::create` with default permissions, so that copy lands mode 0644 outside the vault.

<details>
<summary>Issues (5)</summary>

1. **Normalizer is not the round-trip of the store** — `normalized_field_value` diverges from the stored value for any `due` or `tags` value containing whitespace, so a correct write fails verification and is rolled back. Derive the expected value by rendering then reparsing the item (the path `update` actually takes), or reject such values before writing.
2. **Whitespace in `due`/`tags` corrupts the title** — the extra token is absorbed into the title by `parse_task_line` before verification fails; if `restore_raw` then fails, the mangled title persists. Validate the argument up front rather than relying on rollback.
3. **Orphan recovery file on a restored rollback** — `write_rolled_back` reports `recovery_point` only when `restored` is false, and nobody discards the file when the restore succeeds, leaving unreported cleartext user content under `~/.ctrl/state`. Discard it once the restore is confirmed, or report its path.
4. **Recovery files are world-readable** — `File::create` leaves mode 0644 on a copy of the user's note outside their content tree. Create it with restrictive permissions (0600) and the containing directory 0700.
5. **No direct tests for the new line-editing helpers** — `splice_line`, `remove_line`, `terminator_of`, and `normalized_field_value` are exercised only through `update`/`delete`. The normalizer defect is exactly what a round-trip test over these would have caught.

### Prior findings, each verified by running the code

**A — CLOSED.** `capture` takes `scope: &std::path::Path` and keys on it:

```rust
let key = format!(
    "{:x}",
    Sha256::digest(format!("{}\n{resource}", scope.display()).as_bytes())
);
```

`two_roots_holding_the_same_relative_note_get_separate_recovery_points` captures `/vault-a` and `/vault-b` for the same `ctrl://local/task/Inbox.md`, asserts the locations differ, and asserts the first file still reads `content of a\n` — the part that matters, since `File::create` truncates. `cargo test --lib -- task_resource:: record_write:: tasks_source::` reports `42 passed; 0 failed`. The 3/3 failure is gone.

**B — CLOSED in the reviewed file.** `discard()` removes the file, `a_discarded_recovery_point_leaves_nothing_behind` asserts the path is gone afterward, and `task_resource::produce` calls `recovery.discard()` after `debug_assert!(outcome.is_verified_success())`. Not closed on the restored-rollback path — see below.

**C — CLOSED.** All seven `RecoveryPoint::capture` call sites pass a root explicitly; the four in `record_write.rs` tests pass `tempfile::tempdir()`. The owners expose `with_recovery_root`, and the task owner's test helper uses `root.path().join("recovery")` with a comment naming exactly this hazard. `default_recovery_root()` is reached only from the production constructors.

**D — CLOSED.** `rejoin` is gone. `splice_line` walks `split_inclusive('\n')` and re-emits `terminator_of(piece)` for the addressed line only. Confirmed on a real note: `"# H\r\n- [ ] a\r\n- [ ] b\n"` updated at line 1 yields `"# H\r\n- [x] a ✅ 2026-06-30\r\n- [ ] b\n"` — CRLF lines keep CRLF, the LF line keeps LF. `a_note_with_mixed_line_endings_keeps_each_line_as_it_was` and `a_crlf_note_with_frontmatter_changes_only_the_addressed_line` both pass.

### The requested edge cases

Driven through the public `update` / `delete` against real notes:

| input | result |
| --- | --- |
| `"# H\n- [ ] a"`, delete 1 | `"# H\n"` |
| `"- [ ] only"`, delete 0 | `""` |
| index 9, `update` and `delete` | `LineOutOfRange` both |
| `""`, delete 0 | `LineOutOfRange` |
| `"# H\r- [ ] a\r- [ ] b"`, update 0 | `NotATask` (one line) |
| `"- [ ] a\r"`, update 0 | `"- [x] a ✅ 2026-06-30\r"` |

Had the helpers split on a bare `\r` while `lines()` did not, the two enumerations would have drifted and `update` would have rewritten the wrong line. Deleting a final line that has no newline now yields `"# H\n"` where the old code yielded `"# H"` — the byte-preserving contract working as documented (the surviving line keeps its own terminator), not a regression. For content that legitimately ends in `\r` inside a CRLF file, `terminator_of("a\r\r\n")` returns `"\r\r\n"`, so the splice reproduces the original bytes.

### The normalizer does not describe the store

The docstring makes a specific claim:

> This is that comparison's other operand, derived from the same code that does the storing so the two cannot drift.

It is not derived from that code. It reimplements a subset of it:

```rust
pub fn normalized_field_value(field: &str, value: &str) -> Option<String> {
    match field {
        "status" => Some(normalize_status_word(value)),
        "due" | "title" => Some(value.trim().to_string()),
        "tags" => Some(parse_tag_list(value).join(" ")),
        _ => None,
    }
}
```

What stores the value is `render_item` writing a single line, then `parse_task_line` reading it back — and that pair is lossy for whitespace, because the rendered markers are whitespace-delimited. Observed:

```
update due = "2026-08-10 maybe"
  on disk:    "- [ ] task one 📅 2026-08-10 maybe"
  normalized: "2026-08-10 maybe"
  stored:     due="2026-08-10"  title="task one maybe"

update tags = "two words, ok"
  on disk:    "- [ ] task two #two words #ok"
  normalized: "two words ok"
  stored:     tags="two, ok"    title="task two words"
```

The owner compares `normalized_field_value` against `field_value(current, field)`, finds them different, and takes the clause-6 branch: restore the raw bytes and report `write_rolled_back`. No false success, but two things follow. The user gets `write_rolled_back` on an operation the source was willing to perform, marked `retryable: true`, so the retry fails identically. And the note is genuinely corrupted between the write and the restore, with the leaked token moved into the title; that damage is undone only if `restore_raw` succeeds. When it does not, the reply is `rollback_failed` and the note keeps a mangled title.

The defect is confined to `due` and `tags`: `normalize_status_word` collapses to one of three whitespace-free words, and `title` is the field that absorbs the overflow.

The fix that cannot drift is to compute the expected value the way the store does — render the mutated item, reparse it, read the field off the result. Rejecting whitespace-bearing tags and non-date `due` values before the write is also defensible and would turn a rollback into an `InvalidPayload` the caller can act on.

### The recovery point outlives its purpose on one path

`write_rolled_back` attaches the location only in the `else`:

```rust
} else {
    feedback.code = "rollback_failed".to_owned();
    ...
    if let Some(recovery) = recovery {
        feedback
            .details
            .insert("recovery_point".to_owned(), json!(recovery.location()));
    }
}
```

When `restored` is true the file is not mentioned, and `task_resource::produce` returns immediately after building the outcome — `recovery.discard()` sits past that early return, on the success path only. So a restored rollback leaves a full copy of the note at `~/.ctrl/state/record-recovery/<hash>.bak`, with no reply naming it and no code deleting it. Repeated across writes, that is the accumulation finding B described, reached by a narrower route. `discard` consuming `self` is the right shape for making this hard to get wrong; the missing piece is that the restored branch never calls it. The unverifiable-reread path keeps the file deliberately and reports its location — there the copy is the only way back.

### Recovery files are created with default permissions

```rust
let mut handle = std::fs::File::create(&path).map_err(|_| unavailable())?;
```

No mode is set here or on the `create_dir_all` above it, so the `.bak` lands 0644 in a 0755 directory. The file's whole purpose is to hold a verbatim copy of the user's note outside the tree they chose for it. Single-user desktop keeps the severity low; the cost of `OpenOptions::new().mode(0o600)` and a 0700 directory is lower.

### Test coverage

The new helpers are covered indirectly at the owner level — `a_crlf_note_keeps_its_line_endings`, `a_note_with_mixed_line_endings_keeps_each_line_as_it_was`, `a_multi_tag_write_verifies_instead_of_rolling_back`, `a_status_synonym_verifies_instead_of_rolling_back` — which is why D is genuinely closed. But the passing tags test uses `"work, home"`, single-word tags either side of the comma, so it exercises the one shape where the normalizer agrees with the store. A test asserting `normalized_field_value(f, v)` equals the field read back after `update(.., f, v, ..)` across a few awkward values is what closes the gap, and it is the test that would have failed on `"two words, ok"`.

Not tested: whitespace-bearing `due` and `tags` round-trips; the restored-rollback recovery-file lifecycle; `default_recovery_root()` (correctly avoided, since exercising it means writing to the real `$HOME`).
