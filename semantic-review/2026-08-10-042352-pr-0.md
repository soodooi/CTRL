# Canonical smart-table Resource owner — one bounded cell write under the §15.2 contract

`table_resource.rs` makes one table note a Resource (`ctrl://local/table/<table note>`) with a single produce operation, `set_cell`, addressed by row index in `query` order. The owner hashes the note's whole bytes as the revision, holds one per-note lock from `vault_write_lock::for_path` across recheck → capture → write → reread → rollback, captures the previous bytes outside the vault before touching anything, verifies against `SmartTable::normalized_cell_value` rather than the raw request, rereads through `resource.without_revision()`, and restores byte-exactly through `vault::restore_raw`. Three of the four sibling defect classes are absent; the fourth is present and costs more here than it did in the calendar owner.

Watch for: a one-cell change **deletes the note's prose** — a paragraph above the table and a `## Notes` heading with a bullet below it are both gone after setting one `amount`, because the body is regenerated from `serialize_body()`, and the write is reported as a verified success (**confirmed** by running the owner); the frontmatter is re-rendered from parsed JSON in the same write, so a comment, a quoted title, a flow list, and the schema's two-space indent are all destroyed, and CRLF is flattened across the whole file (**confirmed**); `query`/`describe` on a table note that is a **symlink out of the vault** returns the outside file's contents, where `note_resource` refuses the identical shape through `StableRoot::open_beneath` (**confirmed** — both owners driven against the same layout); and the row/column path the recorded gap names is worse than "no revision precondition" — the viewer commits the whole file through the gate's `vault_write`, the one vault mutator that takes no clause-7 lock, so it can land *inside* this owner's critical section and drive a rollback that destroys both writes (**confirmed** that the lock is absent).

**Verdict**: NEEDS_CHANGES

## High-level view

The sibling fixes carried over. Verification compares against `normalized_cell_value`, which computes the stored form by actually storing it — set the cell, serialize, reparse — so it cannot drift from the store because it *is* the store, and it fails closed on a value that would break the row's shape, refusing a newline before anything is written rather than corrupting the table and rolling back. The reread goes through `without_revision()`, so a revision-pinned ref still reports a verified success, and `RecoveryPoint`'s `Drop` removes the cleartext copy on every path except a failed rollback.

The fidelity class is present, and where the calendar damage was bounded to frontmatter formatting, here the body is rebuilt from the parsed rows, so any content in a table note that is not the pipe table is deleted. Frontmatter is written back as parsed JSON in the same call, which preserves extra schema keys and render-level type sugar as *values* — `type: currency` and `width: 120` both survive, which the in-place schema patch exists to protect — while destroying comments, quoting, collection style, and indentation. Every one of those losses is reported as a verified success, because clause 5's reread inspects only the changed cell.

Row addressing by index holds on the kernel side. The revision covers the whole file, so any concurrent insert, delete, or reorder moves it and a stale index fails the precondition and writes nothing. The hole is reopened by the caller: `record-write.ts` re-reads the revision immediately before producing, so the row index comes from the grid the user is looking at while the revision comes from disk at click time. An insert between render and click therefore passes a precondition computed from bytes the user never saw, and the write lands on the wrong row.

The row/column claim in the gap declaration is real but mischaracterized. The path is not the bespoke gate tool — those all take the lock — it is the viewer's own whole-file `commit`, which serializes client state through `vault_write`. Two things are missing there, not one: the revision precondition the declaration names, and the clause-7 lock it does not. The missing lock is the more serious of the two, because it turns this owner's rollback into a second act of data loss.

Two smaller gaps. `produce` skips the row-bounds check that `stage` performs, so the same out-of-range request is explained two different ways depending on which verb you call. And clause 6's rollback branch is unreachable through any value I could construct, so the one clause that protects the user's content on a mismatch is exercised by no test through this owner — while the concurrent writer above is exactly what makes it fire in production.

<summary>Issues (10)</summary>

1. **A one-cell write deletes the note's prose** — the body is replaced by `serialize_body()`, so a paragraph above the table and a heading plus bullet below it are gone after a single `set_cell`, reported as a verified success. Preserve the text outside the table's line span, or refuse a table note carrying content the serializer cannot round-trip.
2. **Frontmatter is re-rendered from parsed JSON** — the same write destroys a comment on an untouched key, unquotes `title: "Budget 2026"`, expands `tags: [money, ops]` to a block list, and reflows the schema's two-space indent to zero. For a cell edit the fix is to not rewrite the frontmatter block at all, since the operation does not change it; `vault::patch_frontmatter_key` preserves these but commits with a plain `fs::write`, which would regress clause 4.
3. **CRLF is flattened across the whole file** — a CRLF table note comes back entirely LF, reported as a verified success. Unlike the calendar case there is no mixed-ending file, because both halves are rewritten; the note is simply converted.
4. **`query`/`describe` read outside the vault through a symlinked table note** — `read` uses `vault::read` plus `vault::read_raw`, both plain path reads, so a `tables/x.md` symlink to a file outside the root returns that file's rows. `note_resource` refuses the identical layout via `StableRoot::open_beneath`. Resolve through the same stable handle. The write is contained (the rename replaces the link with a regular file) but silently destroys the user's symlink.
5. **The gate's `vault_write` takes no clause-7 lock** — it is the only vault mutator that does not, and it is the tool the viewer's row/column `commit` uses. It can therefore execute between this owner's commit and its reread, so the owner observes bytes it did not write, restores its pre-image, and the reply says `write_rolled_back` — losing the viewer's row operation *and* the cell write. Give `vault_write` the same `vault_write_lock::for_path` guard every other writer takes.
6. **The viewer's row/column operations rewrite the whole file from client state with no precondition** — nine callbacks (delete row, batch delete, move, duplicate, add/update/delete column, save/replace views, form submit) call `commit(...)`, which serializes the possibly stale in-memory table and overwrites the file. A cell write that landed since the grid loaded is discarded with no conflict reported. Route these through bounded `produce` operations, or condition the whole-file write on the revision the client rendered.
7. **The revision the caller conditions on is not the one it rendered** — `writeRecord` calls `readRevision(ref)` immediately before `produceResource`, so an insert between grid render and click passes the precondition while the row index is already stale, and the write lands on a different row than the user clicked. Pass the revision the grid was rendered from instead of re-reading it.
8. **`produce` skips the row-bounds check `stage` performs** — for row 9 of a one-row table, `stage` returns "row 9 is past the end of this table (1 rows)" and `produce` returns "that value cannot be stored in item", which points at the value rather than the index. Move the bounds check into the shared path.
9. **Clause 6 is unreachable by value and untested** — 27 probe values (pipes, backslashes, escaped pipes, tabs, U+2028, NUL, a 480-character string, leading/trailing separators) all verified, so no input drives the rollback. None of the 13 tests covers rollback, the recovery-point lifecycle, fidelity, or CRLF. Add a rollback test that injects a mismatch, and a fidelity test asserting the note's prose survives.
10. **No size bound on the read** — a 549 KB, 40,000-row table parsed and returned in full, where `note_resource` refuses past `MAX_MARKDOWN_BYTES`. Also minor: a missing table note reports `Unavailable { OwnerUnavailable, retryable: true }` rather than a not-found, so a caller retries a note that does not exist; and `stage` calls `refuse_unstorable` twice, the first result discarded.

### The delegated writer rebuilds both halves of the note

The owner's comment says a cell edit touches rows only, so "frontmatter is written back untouched and every column keeps its render-level type and any extra keys". The second half is true as far as *values* go. The first is not, in either half:

```rust
super::vault::write(
    self.root()?,
    &path,
    &opened.table.serialize_body(),   // the body is REGENERATED from parsed rows
    &opened.frontmatter,              // re-rendered from parsed JSON by vault::write
)
```

`serialize_body` emits header, separator, and one line per row — nothing else. Running one `amount` change against a table note that carries ordinary prose (**confirmed**):

```
BEFORE                              AFTER
---                                 ---
schema:                             schema:
  - key: item                       - key: item
    label: Item                       label: Item
    type: text                        type: text
  - key: amount                     - key: amount
    label: Amount                     label: Amount
    type: number   # keep me          type: number
title: "Budget 2026"                title: Budget 2026
tags: [money, ops]                  tags:
---                                 - money
                                    - ops
Some prose above the table.         ---

| Item | Amount |                   | Item | Amount |
| --- | --- |                       |---|---|
| Rent | 1200 |                      | Rent | 1300 |
| Coffee | 40 |                      | Coffee | 40 |

## Notes below the table
- a bullet the user wrote
```

Measured on that run: prose above kept `false`, heading below kept `false`, bullet below kept `false`, frontmatter comment `false`, quoted title `false`, flow tag list `false`, two-space schema indent `false`, `| --- |` separator spacing `false`, new value written `true`, `is_verified_success()` `true`.

The body loss is what distinguishes this from the calendar finding. There the write reformatted the user's file; here it deletes content. A table note is often more than its table — a description above the grid, working notes below it — and nothing in the ref, the descriptor, or the reply warns that `set_cell` owns the whole body.

What *does* survive matters for choosing the fix: `type: currency` and a non-schema key like `width: 120` both come back intact, because the owner passes the frontmatter through as parsed JSON rather than regenerating it from `serialize_schema()`. The render-level type sugar is safe; the YAML text around it is not.

A CRLF table note is converted outright rather than left mixed (**confirmed**): `"---\r\nschema:\r\n…| Rent | 1200 |\r\n"` comes back as `"---\nschema:\n…| Rent | 1300 |\n"`, `is_verified_success()` true, no `\r\n` anywhere.

One shape the sibling got wrong is right here: a plain note with no schema is refused rather than converted, because `normalized_cell_value` returns `None` when no field matches, and the file is left byte-identical (**confirmed**).

### A symlinked table note reads outside the vault

`read` resolves by path, twice:

```rust
let entry = super::vault::read(self.root()?, &path).map_err(|_| unavailable())?;
let raw = super::vault::read_raw(self.root()?, &path).map_err(|_| unavailable())?;
```

`sanitize_relative_path` rejects `..` traversal in the *ref*, and `table_path` rejects it again, but neither looks at what the final component is on disk. Driving both owners against the same layout — a note in the vault that is a symlink to a file in another directory (**confirmed**):

```
table owner : QUERY THROUGH SYMLINK OK -> rows=[{"item":"OUTSIDE-SECRET"}]
note owner  : REFUSED -> Unavailable { reason: OwnerUnavailable, retryable: false }
```

The write is contained: `write_atomically` renames a staged sibling over the vault path, which replaces the link rather than following it, and the probe confirms the outside file was unchanged while the vault entry stopped being a symlink. So the exposure is read-side — `query` and `describe` return content from outside the authorized root — plus a silent loss of the user's own link. Clause 2 asks for a freshly resolved *stable handle*; this owner uses a path string, and the same `StableRoot::open_beneath` the note owner already uses would close both halves and collapse the two reads into one.

Collapsing them is the second reason to do it: two reads mean the revision, the parsed rows, and the recovery-point bytes can come from different states of the file if anything writes between them (**likely** — it follows from the two reads plus the missing lock below; I did not construct the interleave).

### The row/column path: the missing lock, not just the missing precondition

The recorded gap says row and column operations "still rewrite the whole file without a revision precondition". True, and the path is not where the wording implies. Every bespoke gate tool — `smart_table_produce`, `update_cell`, `append_row`, `delete_row`, `add_field`, `delete_field`, `batch_*`, `add_view` — takes `self.vault_write_lock(&args.path)` before reading. They read fresh under the lock, so they cannot lose a committed cell write, though a stale index handed to `delete_row` still deletes the wrong row with no precondition, no staged facts, and no recovery point.

The real path is the viewer's own `commit`:

```
SmartTableViewer
  onCellChange  ──▶ commitCell ──▶ setTableCell ──▶ produce(set_cell)   [locked, precondition, recovery point]
  onDeleteRow   ─┐
  onDeleteRows  ─┤
  onMoveRow     ─┤
  onDuplicateRow─┼─▶ commit(next) ─▶ writeVault ─▶ gate vault_write ─▶ vault::write
  onAddColumn   ─┤                                  ▲
  onUpdateColumn─┤                                  └─ no lock, no precondition, no recovery point
  onDeleteColumn─┤
  onSaveView    ─┤
  onSubmitForm  ─┘
```

`vault_write` is the one vault mutator in the gate that takes no guard — verified by listing every `vault_write_lock::for_path` call site in the tree; the four Resource owners and 20-odd tool sites take it, `vault_write` at line 3144 does not. Clause 7's own note in the ADR is explicit that this is not allowed: "a legacy bespoke vault write must serialize against a canonical `produce` on that file rather than holding a separate lock." Holding no lock is the wider version of the case it names.

The loss has two stages. The ordinary one: the viewer serializes `table`, which came from a `['smart-table-file', path]` query invalidated only by the viewer's own writes, so a cell write committed by Irisy or another window since the grid loaded is silently discarded — the same defect the v90 changelog says was closed for cell edits, still open for row and column edits, and now asymmetric within one component.

The one the missing lock adds: because `vault_write` does not wait for the guard, it can commit between this owner's `vault::write` and its reread. The owner then reads a cell that does not carry `expected`, takes clause 6, and calls `restore_raw` with the pre-image it captured — which reverts the viewer's row deletion *as well as* its own cell write, and reports `write_rolled_back` naming only the cell. Clause 7 exists precisely so that "the loser's rollback would revert content the winner already reported as verified" cannot happen; one unlocked writer reintroduces it (**likely**, by construction from the confirmed lock absence).

### Row addressing: the kernel closes it, the caller reopens it

The revision is `sha256` of the whole file, so any insert, delete, or reorder moves it. Driving a concurrent insert at the top between the caller's read and its write (**confirmed**):

```
outcome code = precondition_failed, verified = false
file unchanged: | Insurance | 90 |  /  | Rent | 1200 |  /  | Coffee | 40 |
```

The cost is deliberate over-strictness — an edit to a *different* cell also fails the precondition — and `table-write.ts` says so plainly.

The caller undoes it. `writeRecord` fetches the revision itself, immediately before the write:

```ts
expectedRevision = await readRevision(ref);          // fresh from disk, at click time
const outcome = await produceResource(ref, operation(expectedRevision));
```

while `rowIndex` reaches it from the rendered grid through `__idx`, which is correctly the canonical parse-order index, so sorting and filtering do not misdirect the write. The mismatch is in *time*, not in space: the index describes the table the user saw, the revision describes the table on disk now. An insert between render and click leaves the precondition satisfied by construction and the write landing on the neighbouring row. The owner's `target` label would name the row it actually hit, which is the one honest signal, but nothing rejects the write.

### Clause 6 has no reachable input, and the tests do not reach for it

The rollback branch requires `observed != expected`, where both derive from `normalized_cell_value` — which sets the cell, serializes, reparses, and returns `None` if the row count changed or any neighbouring cell moved. I probed 27 values — `with | pipe`, `a\|b`, `\`, `x\`, `|`, `||`, `-`, `---`, `-- | --`, `| leading pipe`, `trailing pipe |`, tabs, `#hash`, `**bold**`, U+2028, NUL, a 480-character string, empty, whitespace-only, `café` — and every one either verified or was refused before any write. None reached clause 6.

So the branch that protects the user's content is unexercised by any test in the file. The 13 tests cover the descriptor, the read, a verified write, staging, a stale revision, an out-of-range row, a newline refusal, a padded value, a pipe round trip, an unknown column, a column op refusal, authorization, and a traversing ref — nothing for rollback, the recovery-point lifecycle, fidelity, or CRLF. Given the concurrent writer above is the realistic trigger, that is the gap worth closing first: inject a writer that stores a different value, assert `write_rolled_back`, and assert the note came back byte-identical.
